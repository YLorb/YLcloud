## 第一层网关设计约束

- 独立模块 `src/cloud-gateway`，使用 Spring Cloud Gateway Server WebFlux / Reactor Netty，独立管理 Boot parent 与 Cloud BOM；不将网关依赖加入 cloud-server。
- 一套对外网关部署配置，可横向扩展实例；保留 Nginx 的静态资源职责，将 API 请求转发至网关。按服务建立显式路由，现有 cloud-server 的 `/api/**` 保持路径兼容。
- Redis 作为独立容器服务部署并配置健康检查、凭证、连接与操作超时；仅内网可达。网关实例共享限流状态，现有 Session 仍由后端数据库管理。
- 按已确认的严格滑动窗口约束设计 Redis 限流，取代此前令牌桶方案。拟采用有序集合记录已放行请求时间，服务端原子完成过期清理、计数判断和写入；统一时间源，保证并发和多网关实例下共享额度。被限流拒绝的请求不写入已放行记录，不将其重试变成不断延长的封禁。不把未验证的客户端身份当作用户级限流依据。
- 限流键以可信客户端 IP 为主体，不按路由分别分配 60 次额度。一次请求只扣一次，后端返回错误仍属于已放行请求。共享公网出口的用户共享额度，后台轮询和多个上传分片均会消耗额度，前端应处理 429 及 Retry-After，避免立即重复请求。
- Redis 超时、连接失败及限流执行失败均需验证返回 503 且请求未到达上游；不能仅凭 Redis 健康检查或框架默认行为声称实现故障拒绝。
- 全代理按服务清单落实，不等于公开服务所有接口。盘点各服务公开路径与既有鉴权；无现成对外鉴权的内部接口记录为待处理项，不在本阶段无条件开放。
- Session Cookie、Set-Cookie、既有 API 凭证和 CSRF 头正确透传；仅信任明确配置的入口代理转发头。
- 后端登录限流当前使用 remoteAddr，接入网关时同时验证可信客户端地址传递，避免所有用户被合并为网关 IP 的来源额度。
- MinIO 代理/直链两种模式都必须经过现有权限判定后生成访问入口。直链模式使用有有效期的预签名链接，不将桶改为公共；代理模式核对 Host、路径与签名兼容，不接受客户端任意指定上游 URL。已经签发的直链是否立即失效取决于存储端能力，不能承诺切换模式即撤销历史链接。
- 流式转发文件与长响应，按路由配置超时；避免完整缓存请求体及自动重试有副作用的请求。
- 生产网络限制外部直接访问上游端口，同时保留业务服务之间必要的直连通信；禁止用收紧端口破坏服务间调用。
- 部署同时覆盖本地 Compose、镜像 Compose、Nginx、Vite 和 CI；路由回滚恢复此前前端代理目标。下载模式优先复用既有后台设置持久化机制；若需要新增配置初始化，保持向后兼容并纳入回滚说明。
