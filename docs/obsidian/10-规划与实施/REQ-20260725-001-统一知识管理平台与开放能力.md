# 统一知识管理平台与开放能力

## 状态说明

本文已于 2026-07-25 完成首轮产品决策清零，并于 2026-08-16 追加 Space 文件树体验、在线查看和贡献者可见性要求，是下游架构与实施计划的需求基线。需求状态保持 `pending`，直到实现、测试和验收全部完成。

## 产品愿景

将 YLcloud 建设成可独立私有部署、也可由官方运营为共享 SaaS，面向个人和小团队的 AI Knowledge Workspace。系统以文件生命周期为主线：个人网盘负责通用文件管理和未知识化文件暂存，Space 负责协作、权限与默认知识化；RAG、知识画像、AI Assistant、Workflow 和受控 Agent 只能消费当前主体有权访问的知识，并通过版本化开放 API 与 Webhook 支持 Web、桌面端、移动端和第三方系统访问。

## 用户与业务价值

- 个人用户可以保存未知识化的个人文件，也可以把选定文件导入 PERSONAL Space 形成个人知识库。
- 团队用户通过 TEAM Space 统一管理团队文件、成员权限和知识资产。
- AI Assistant 可以在显式授权的知识范围内检索、回答和调用 Agent。
- 第三方应用通过用户创建的 API Key 使用与 Web 核心能力基本一致的文件、知识和 Agent 能力。
- 部署管理员管理账号、用户组、配额、站点和运行策略。
- 部署所有者对实例承担最终责任并拥有超越普通资源权限的私人数据访问能力。

## 范围

### 包含

1. 单实例部署所有者、ADMIN、USER、用户组和 Space 资源权限。
2. 个人网盘与 Space 两套独立逻辑文件模型。
3. PERSONAL/TEAM Space 生命周期与所有权。
4. Space 文件自动知识化以及移出 Space 后的知识清理。
5. Web/API Key 的 Agent 低风险与高风险预授权。
6. 用户级 API Key、目录/Space 范围、版本化开放 API。
7. Webhook 事件订阅、签名、重试和幂等。
8. AI 知识资产自动生效与 `NEEDS_REVIEW`。
9. 账号注销、恢复期、数据清理和数据导出。
10. 用户组配额与用量统计。
11. 在线完整备份、临时恢复验证、手动升级和回滚。
12. 可配置安全审计保留。
13. Space 文件当前版本与历史版本的受权在线预览。
14. Space 文件提交人、最后修改人及对应时间的可见性。
15. Space 目录树浏览，以及与个人网盘一致的 File Explorer 核心交互。

### 非目标

- 完整租户模型和 `tenant_id` 全表隔离。
- 共享 SaaS 中的企业级独立管理员边界。
- 首阶段支付、订单和自动计费。
- 首阶段 Kubernetes、多节点高可用、零停机升级和跨区域容灾。
- 软件层强制 HTTPS 或内置证书签发。
- 部署所有者专用密码、恢复 Secret 或产品内最高权限恢复流程。

## 已确认业务规则

### 单实例与交付形态

1. 私有部署与官方共享 SaaS 使用同一产品内核和同一权限法则。
2. 不实现完整租户模型；需要组织级强隔离的客户使用独立部署。
3. 软件层不强制 HTTPS；部署者可以自行配置 Nginx、Caddy 或其他 TLS 终止。

### 部署所有者与管理员

1. 空实例直接开放普通注册入口，第一个成功注册的用户成为唯一部署所有者并同时具有 ADMIN 身份。
2. 部署所有者自行设置普通账号密码，不设置独立“部署所有者密码”。
3. 部署所有者身份永久绑定且不可转移、删除、停用或降级。
4. 部署所有者可以不受个人所有权、Space 成员关系等普通资源权限限制，无限制访问实例内私人数据。
5. 普通 ADMIN 默认不能读取个人网盘、PERSONAL Space、会话、长期记忆或 TEAM Space 内容。
6. 普通 ADMIN 读取个人数据需要用户授权；读取 TEAM Space 内容需要 OWNER 授权。
7. 部署所有者访问可以审计，但审计不能构成访问限制。
8. 用户已明确接受部署所有者可以访问私人数据的全部隐私和安全风险。
9. 现有实例升级时，将 `user_id` 最小的用户设为部署所有者；如果该账号已停用，升级过程自动恢复为启用状态。

### 文件与 Space

1. `user_file` 个人网盘与 `space_file` Space 文件保持两套独立逻辑模型，共享 `file_info` 和物理对象时不得复制字节。
2. 个人网盘文件不自动知识化。
3. 每个用户创建时自动获得且仅获得一个 PERSONAL Space。
4. PERSONAL Space 永远个人私有，禁止邀请成员、转让、退出、删除或转换为 TEAM Space。
5. 用户可以创建和加入多个 TEAM Space。
6. TEAM Space 始终且仅有一名 OWNER；OWNER 可以把所有权原子转移给有效成员。
7. 有其他成员时 OWNER 必须先转移所有权才能退出。
8. 只有 OWNER 一人时，“退出”转为“解散”，必须显示高风险确认窗口。
9. 文件直接上传、从个人网盘导入或通过 Web 链接导入 Space 后自动进入该 Space 的知识库。
10. Space 文件索引失败时文件继续存在，但必须显示知识处理失败且不可检索。
11. 停止检索某个文件的唯一业务方式是将文件移出 Space。
12. 移出 Space 后清理该 Space 的 RAG 引用、向量和知识资产，不影响个人网盘原文件或其他 Space 引用。
13. 物理内容只有在个人文件、Space 文件和版本记录全部解除引用后才能清理。
14. 具有 Space 读取权限的成员可以在 Space 文件页面在线查看支持预览的当前文件与历史版本；文本、图片、PDF、音频和视频沿用受权预览能力，不支持的格式必须明确提示并保留下载入口。
15. 预览必须在当前 Space 授权边界内完成，不能生成绕过成员权限的公开链接；文件被移出、成员权限被撤销或版本失效后，后续预览请求必须立即拒绝。
16. Space 文件列表必须显示“提交人、提交时间、最后修改人、最后修改时间”；版本历史必须显示每个版本的提交人和提交时间。文件夹节点在创建、重命名和移动等适用操作中沿用相同贡献者规则。
17. “提交人”是首次把该逻辑文件加入 Space 的实际用户，来源包括直接上传、从个人网盘导入和 Web 链接导入；该字段创建后不可被后续版本、重命名、移动、知识处理或系统任务覆盖。
18. “最后修改人”是最近一次成功改变文件内容或用户可见元数据的实际用户。计入动作至少包括上传新版本、恢复历史版本、重命名、移动和修改文件版本设置；新建时最后修改人与提交人相同。
19. 自动 RAG 索引、知识状态/错误状态更新、对账、清理任务及其他纯系统状态变化不得更新最后修改人或用户修改时间。
20. 用户身份展示使用安全的显示名称，并保留稳定用户 ID 作为重名、改名、停用或注销后的识别依据；不得因此暴露邮箱、手机号或其他无关账号信息。历史记录无法可靠归因时显示“未知”，不得根据通用 `updatetime` 猜测修改人。
21. 个人网盘与 Space 保持 `user_file`、`space_file` 两套逻辑模型，不以 UI 复用为由合并授权规则、逻辑节点或业务生命周期。
22. 个人网盘文件默认不解析、不向量化；文件进入 Space 后默认自动进入该 Space 的知识化链路，首阶段不提供逐文件关闭知识化的开关。
23. Space 文件页以当前目录为浏览上下文，支持进入文件夹、返回上级、面包屑、目录内上传、目录内个人文件导入、创建文件夹和当前目录列表；不得继续把全 Space 文件平铺表格作为唯一主视图。
24. Personal 与 Space 可以复用 File Explorer 的展示组件和交互规范，但必须传入不同的数据适配器、操作能力和授权上下文；Personal 所有权判断不得替代 Space 成员角色判断。
25. 当前阶段文件可见性仍按 Space 级 OWNER/ADMIN/MEMBER 角色控制，不开放文件级 ACL 配置；接口和前端边界应避免固化“Space 成员必然永久可见全部文件”的假设，为后续文件/文件夹 ACL 与继承策略预留扩展点。
26. 当前用户无权访问的 Space 不得出现在知识库范围选择中。后续引入文件级 ACL 时，Space 文件清单、知识检索、AI 问答和引用返回必须复用同一文件可见性判定，不允许先全量检索再仅在前端隐藏来源。

### AI 知识资产

1. 摘要、标签、分类、问题和知识画像通过结构与质量校验后直接成为当前有效资产。
2. 低置信度、冲突或校验失败的结果进入 `NEEDS_REVIEW`。
3. 来源、模型、版本、修订和审计记录需要保留。

### Agent 与高风险授权

1. Agent 可以在预授权资源范围内自动执行创建目录、添加标签、生成草稿、移动到回收站等可恢复低风险操作。
2. 永久删除、不可逆覆盖、公开分享、权限变更和外部发送属于高风险操作。
3. Web 对话和 API Key 都支持 `ALLOW_ONCE` 与持久预授权。
4. 用户可以使用单一“允许高风险操作”总开关，不按具体高风险动作分别授权。
5. 命中有效高风险总授权后，不再要求逐项或逐次确认。
6. 高风险总授权是动态风险等级授权，自动覆盖未来新增的全部 HIGH_RISK Tool。
7. 执行时仍需检查当前用户权限、API Key Scope、目录/Space 范围、有效期、撤销状态、限流和站点策略。
8. 用户已明确接受凭据泄露、误授权和未来能力自动扩大的风险。
9. API Key 的“允许高风险操作”只授权 Agent 调用 HIGH_RISK Tool，不直接授予永久删除、公开分享或成员权限变更等高风险 REST API。
10. HIGH_RISK Tool 可以在该次已预授权的 Agent 调用中执行其声明的底层操作；所有操作仍受 Tool 风险等级、Key Scope、资源范围和当前账号权限约束。
11. Web 持久高风险授权按账号全局生效，覆盖该账号下全部 Agent 和对话。
12. Web 持久高风险授权允许永久有效，直到用户主动撤销；交互体验参照桌面端应用的持久授权管理。
13. 升级到高风险总授权模型时，全部撤销现有 `workflow_confirmation_grant`，不得自动扩大或转换旧授权；用户必须按新模型重新授权。

### 用户 API Key

1. API Key 在用户统一安全设置中创建，不独属于云盘或知识库。
2. 云盘能力与知识库能力可以独立开启。
3. 云盘权限显式选择只读/写入并绑定一个根目录及其子树。
4. 知识库权限显式选择检索/Agent 调用，并绑定一个或多个 PERSONAL/TEAM Space。
5. Space 选择器提供“全选”；全选只选择当时可见的 Space，不自动包含未来 Space。
6. API Key 实际权限始终为 Key Scope、资源范围、用户当前权限与系统策略的交集。
7. 用户自行选择到期时间或永不过期；部署管理员可以禁止永不过期、设置最长有效期和每用户数量上限。
8. 高风险总开关可以赋予 API Key 在授权范围内直接执行高风险 Agent 操作的能力。
9. Key 明文只在创建时显示一次，服务端只保存不可逆哈希。

### 开放 API 与 Webhook

1. 开放 API 最终覆盖普通用户 Web 端核心能力：文件管理、Space/知识检索、AI Assistant 和 Agent。
2. 站点配置、用户管理和部署运维不纳入普通用户 API Key。
3. 稳定接口使用 `/api/v1/...` 等路径版本；同一主版本内保持向后兼容。
4. 无版本路径 `/api/...` 默认路由到最新版，第三方生产客户端应固定版本。
5. 破坏性变更发布新主版本，旧版本过渡期由部署管理员配置。
6. Webhook 支持文件、知识索引、Agent 任务和 Space 权限事件。
7. Webhook 采用至少投递一次语义，允许重复且不保证跨资源全局顺序。
8. 每条事件提供唯一 `eventId`、资源版本和时间戳，由第三方幂等处理。

### 注销、清理和导出

1. 用户主动注销后，账号状态立即变更为“注销”并记录注销时间，同时禁止正常使用并隐藏个人数据。
2. 默认恢复期为 3 天，由部署管理员配置。
3. 普通用户仍是 TEAM Space OWNER 时，必须先转移或解散全部 TEAM Space 才能注销。
4. 注销用户不能使用原账号自行恢复；恢复期内由 ADMIN 帮助恢复。
5. 定时任务扫描“注销”状态账号；超过恢复期后提交异步账号删除任务。
6. 异步删除任务永久清理个人网盘、PERSONAL Space、会话、长期记忆、API Key 和相关索引。
7. TEAM Space 中仍被团队引用的文件和知识资产继续保留。
8. 部署所有者不能注销。
9. 用户可以生成异步加密数据导出，包含个人数据以及当前有权并显式选择的 TEAM Space 数据。
10. 导出不得包含 API Key 明文、平台 Secret 或其他用户私有数据。

### 配额与用量

1. 部署管理员通过用户组配置存储容量、单文件大小、Space 数量、API 调用量、模型 Token、Agent 任务数和并发限制。
2. 第一阶段只做配额与用量统计，不实现支付、订单和自动计费。
3. 为未来外部计费系统预留用量查询能力。
4. 相同物理文件无论具有多少个人网盘或 Space 逻辑引用，存储用量只计算一次。
5. API 调用量、模型 Token 和 Agent 任务数按自然月重置。
6. TEAM Space 使用独立于 OWNER 个人用户组配额的 TEAM Space 存储配额。

### 审计

1. 权限变更、API Key、部署所有者数据访问、Agent 高风险操作、导出、注销、备份和恢复需要安全审计。
2. 审计保留期由部署管理员配置并允许永久保留，默认 7 天。
3. 用户已明确接受默认 7 天可能无法覆盖延迟发现安全事件的风险。

### 备份、恢复和升级

1. 单机 Docker Compose 是首版正式生产部署基线。
2. 自动备份覆盖 MySQL、MinIO、Qdrant Snapshot 和必要部署配置。
3. Secret 只有加密后才能进入备份。
4. 默认每天 `04:00 UTC+8` 在线执行，不中断用户访问。
5. 默认保留 1 份成功备份，管理员可以调整。
6. 新备份必须先生成到独立临时目录，完成清单、摘要与可读性校验。
7. 每次备份必须在隔离临时环境中完成完整恢复验证。
8. 新备份恢复验证通过并进入 `READY` 后，才能替换上一份成功备份。
9. 失败或中断不能删除上一份成功备份。
10. 用户已明确接受默认只保留 1 份成功备份的风险。
11. 升级由部署管理员通过受控 Docker Compose 脚本手动发起，禁止静默升级。
12. 升级前必须完成并验证完整备份。
13. 升级允许短时维护模式，拒绝写操作与新 Agent/Workflow 任务，不要求首版零停机。
14. 升级失败使用上一版本镜像与备份执行回滚。
15. 备份只要求对进入备份的 Secret 加密，不要求加密整个备份归档。
16. Secret 加密密钥必须由部署者通过备份目录之外的文件型 Secret 提供。
17. Secret 加密密钥是恢复备份的必要条件，不得被写入备份归档或与备份存放在同一目录。

### Webhook 补充规则

1. 在 API Key Scope 和订阅配置允许时，Webhook 可以包含文件名、问题、回答或 Agent 任务结果等业务内容。
2. Webhook 默认阻止回环地址、链路本地地址和私有网段目标，防止 SSRF。
3. 部署所有者可以通过明确的站点策略为私有部署开放内网 Webhook，并承担由此产生的网络访问风险。

### API 兼容补充规则

1. 部署管理员未配置时，旧主版本 API 默认兼容 30 天。
2. 兼容期结束后，旧主版本 API 继续提供只读访问；所有写操作和会产生副作用的调用必须拒绝。

## 现状证据与差距

### 已有基础

- `users.role`、`AdminPermissionService`、用户组和单用户权限覆盖已经存在。
- 首用户创建由 `user_registration_guard` 串行化，能够避免并发产生多个首管理员。
- `user_file`、`space_file`、`file_info` 和物理清理 Outbox 已经形成双逻辑文件基础。
- PERSONAL/TEAM Space 类型和 OWNER/ADMIN/MEMBER 角色已经存在。
- Space 文件导入后已经自动创建 RAG 文档和索引任务。
- 后端已经提供 Space 当前文件与历史版本的预览元数据和受权流式接口。
- `space_file.created_by` 已保存首次创建用户，`file_version.created_by` 已保存版本创建用户。
- `space_file` 已有 `parent_id`、目录节点、按父目录查询和树形 VO，后端已提供创建文件夹以及上传/导入时指定父目录的基础能力。
- Workflow Tool Registry、风险等级、调用幂等和确认 Grant 已经进入 Java、迁移和测试。
- Compose、自部署脚本、健康检查和发布脚本已经存在。

### 必须替换或扩展

- 当前只有 ADMIN/USER，没有不可转移的部署所有者身份。
- 当前生产部署可通过环境变量 Bootstrap 创建首管理员，与“首个用户自行注册成为所有者”存在冲突。
- 当前 ADMIN 在权限解析中具有全局豁免，需要拆分普通 ADMIN 与部署所有者。
- 当前 PERSONAL Space 成员、删除和设置接口没有统一禁止规则。
- 当前 TEAM Space 不支持所有权转移。
- 当前 Space 删除只禁用一行，尚未实现完整解散状态机。
- 当前 Workflow 高风险 Grant 按 Tool、参数和 30～600 秒 TTL 校验，与动态高风险总授权冲突。
- 当前没有用户 API Key、Scope、目录/Space 白名单和 Key 级用量模型。
- 当前没有版本化开放 API 门面、Webhook、事件 Outbox 和投递状态机。
- 当前没有账号注销恢复期、完整个人数据导出或统一审计清理。
- 当前配额以 USER/ADMIN 角色和个人存储为主，没有用户组全量用量策略。
- 当前没有完整实例在线备份、临时恢复验证、备份轮换或受控升级状态机。
- 当前文档仍把 HTTPS 写成生产必需项，并把所有高风险操作写成本轮确认。
- 当前 Space 文件页面只提供下载和版本入口，没有调用现有预览接口形成在线查看体验。
- 当前 Space 文件 VO/前端类型和列表未暴露 `created_by`；`space_file` 没有独立的最后修改人和用户修改时间，现有 `updatetime` 还会被知识状态等系统变化更新，不能作为贡献者归因依据。
- 当前版本历史虽返回 `createdBy`，但页面没有展示版本提交人。
- 当前 Space 页面调用全量文件列表并平铺成单张表；虽能创建根目录文件夹，但不能进入目录，上传和个人文件导入也未绑定当前目录，后端已有目录能力没有形成可用的文件树体验。
- Personal 与 Space 文件浏览由两套页面分别实现，尚未抽取带数据适配器和权限能力上下文的共享 File Explorer 边界。

## 验收总则

1. 任何实现不得依赖前端隐藏按钮作为安全边界。
2. 用户、API Key、Agent、Webhook 和管理员访问必须能够映射到可审计主体。
3. PERSONAL Space、TEAM Space、个人文件和知识资产不得出现跨用户越权。
4. Space 文件状态与知识可用状态必须分离，失败不得伪装成功。
5. API Key、Webhook 和 Agent 的权限撤销应立即对新请求生效。
6. 高风险总授权行为必须与用户确认的风险接受一致，并在 UI 清晰披露。
7. 备份只有完成隔离恢复验证后才能成为成功备份。
8. 实现 Agent/LLM 必须为每个原子任务补充完整测试用例、执行测试并回写独立测试文档。
9. Space 文件当前版本和历史版本必须能在成员权限内在线预览；权限撤销、文件移出和不支持格式不得产生越权或误导性成功。
10. Space 文件提交人保持不可变，最后修改人只随已定义的用户内容/元数据动作变化；任何自动知识处理不得污染贡献者归因。
11. Space 文件页可以逐级进入目录并通过面包屑返回；新建文件夹、上传和个人文件导入均落入当前目录，刷新后目录关系保持一致。
12. Personal 与 Space 的核心文件浏览交互一致，但所有 Space 查询和写操作仍执行 Space 授权；不得因组件复用产生跨 Space、跨用户可见性或写入旁路。
13. Space 普通文件默认提交知识化任务，目录节点不进入 RAG；个人网盘文件在未导入 Space 前不得因本功能被自动知识化。
14. 知识库范围和当前检索结果只包含用户有权访问的 Space；文件级 ACL 本阶段仅作为扩展边界，不得伪装为已交付能力。

## 风险接受记录

- 接受部署所有者无限制访问私人数据。
- 接受部署所有者身份不可转移且系统不提供专用凭据恢复。
- 接受高风险总授权不按动作细分。
- 接受高风险总授权自动覆盖未来新增 Tool。
- 接受默认 7 天审计保留可能不足以调查延迟发现事件。
- 接受默认只保留 1 份成功备份的单恢复点风险。
- 接受无版本 API 路径随最新版发生破坏性变化。
- 接受旧 API 在兼容期结束后继续暴露只读能力所带来的长期维护与攻击面成本。
