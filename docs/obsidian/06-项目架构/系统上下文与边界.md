# 系统上下文与边界

## 业务上下文

系统围绕三个逐层增强的对象组织：

- 文件：用户拥有或可访问的原始内容。
- Space：团队协作和权限边界，也是知识库的业务边界。
- 知识资产：从 Space 文件派生的 chunk、向量、画像、问题和会话。

个人网盘解决“保存与管理”，Space 解决“共享与授权”，RAG 解决“找到与回答”，知识画像解决“理解、治理和运营”。四者共用文件事实，但失败语义必须隔离。

## 系统参与者

| 参与者 | 权限与意图 |
|---|---|
| 未登录访客 | 访问公开站点信息和有效公开分享 |
| 普通用户 | 管理个人文件，参与被授权 Space，发起知识问答 |
| Space MEMBER | 使用 Space 文件和知识库，不能修改管理配置 |
| Space ADMIN | 管理成员、文件、RAG 配置和知识画像开关 |
| Space OWNER | 拥有最终管理权和 Space 生命周期控制 |
| 平台 ADMIN | 管理全局设置与平台级配置 |
| 运维人员 | 部署、注入 Secret、备份、升级和处理告警 |

## 信任边界

~~~mermaid
flowchart LR
  Public[公网/浏览器] -->|JWT 或分享码| API[应用信任边界]
  API -->|内部网络与凭据| Data[MySQL/MinIO/Qdrant]
  API -->|内部 API| AI[模型与解析服务]
  AI -->|可选供应商凭据| External[外部模型供应商]
~~~

- 浏览器输入、文件名、路径、分享码、Space ID 和模型返回均不可信。
- Controller 只完成协议适配；Service 必须再次执行用户、角色和资源归属校验。
- 模型输出不是结构化事实，必须解析、标准化、校验并可能转入人工审核。
- 预签名 URL 是短期能力凭证，应限制时效与对象范围。

## 系统负责什么

- 文件元数据、逻辑目录、版本、分享、配额和 Space 协作。
- 文件到 RAG_READY 的索引闭环。
- 多路检索、回答、引用和查询审计。
- 可选知识画像、质量治理、审核和版本恢复。
- 跨存储操作的业务幂等、失败隔离、补偿和对账。

## 系统不负责什么

- 不自行实现对象存储或向量数据库底层一致性。
- 不训练 embedding、rerank 或 LLM 模型。
- 不把生成式模型输出当作无条件可信数据。
- 当前不提供企业级多区域容灾、图数据库知识图谱或消息队列平台。

## 边界设计的原因

模型和解析独立部署，可以使用 Python 生态并单独分配 CPU/GPU；业务规则留在 Java，避免多个服务分别决定权限和成功状态。存储各司其职，减少让 MySQL 保存大文件或让 Qdrant 承担业务真相的反模式。
