# 意图识别与 Workflow 服务集成

## 目标

将 `D:\document\new_project` 改造为内部 Docker `workflow-service:8003`，为 `ylcloud-app/cloud-server` 提供受控 Graph Workflow API。Workflow 是 Java 调用的编排工具，负责意图识别、必要任务拆分、Context 充分性判断、Graph 校验/执行、召回编排和受控 Tool 调用，但不生成面向用户的最终回答；最终回答继续由 Java 组织 Context 并调用模型生成。Java 保留用户身份、会话、业务事务、最终回答和业务持久化所有权。

## 已确认业务规则

1. 主意图是唯一最终用户目标；次意图只是完成主目标必需的独立子任务。
2. Context 不足、需要召回、指代未解析是独立状态，不是意图。`MEMORY_RECALL_REQUIRED`、`MISSING_CONTEXT`、`REFERENCE_RESOLUTION` 仅保留旧枚举兼容。
3. `SENSITIVE_DATA_QUERY`、`HIGH_RISK_ACTION`、`POLICY_VIOLATION` 是安全状态；安全阻断优先于召回。
4. 每个主/子任务分别判断 `SUFFICIENT/PARTIAL/INSUFFICIENT/UNKNOWN`；Context 足够时禁止召回长期记忆。
5. 意图置信阈值为 `0.7`。默认最多总调用 4 次，个人记忆配置可设为 `1–10`。超限仍无法判断则跳过长期记忆，基于当前 Context 回答。
6. 普通记忆任务生成“原问题 + 3 条改写 + 每待召回任务 1 条独立 Query”；复杂任务为“原问题 + 5 条改写 + 每任务 1 条独立 Query”。
7. 复杂任务条件：存在必要子任务、多历史对象、跨项目归纳或执行依赖；服务端可向 `COMPLEX` 上调。
8. 候选链路：多 Query 召回 → 按任务候选池 → 加权 RRF → Rerank → 冲突/去重/安全 → 批量语义校验。
9. RRF 初值：原问题 `1.5`、任务 Query `1.2`、改写 Query `1.0`。每 Query 12 条、每任务融合 20 条、Rerank/校验 5 条、每任务最终 5 条、全回答最多注入 12 条。
10. Rerank 或语义校验返回 `null`/空/无合格项时，必须返回非 `null` 空集合，不允许未校验候选进入回答。
11. 冲突记忆按 `updatetime` 最新优先，同时间才比较置信度。最新项立即用于回答，旧项进入幂等后台删除任务。
12. 记忆语义更新新增不可变版本，`supersedes_id` 指向被替代的上一条记忆。
13. Context Snapshot 保留 15 天，包含意图、Context 充分性、实际 Query、最终记忆 ID/版本/哈希和实际注入文本。Retrieval Trace 保留 7 天，只保存候选 `memoryId/version/hash`、Query、分数、排序、淘汰原因和重试，不重复保存候选正文。删除会话时两者立即删除。
14. 快照过期后重试降级为“基于当前上下文重新回答”，前端明示提示，后端保存降级标记、原/新任务 ID 和重建时间。
15. 记忆写入/更新/删除判断交给独立 Tool；意图编排器只根据用户明确表达路由工具。
16. `MEMORY_SAVE/UPDATE/DELETE/CLEAR` 由 Workflow 编排并调用 Java Internal Tool Gateway 中的显式记忆 Tool，不在 Workflow 内重写记忆业务规则。
17. Tool 能力按显式注册、独立 Schema、最小权限和风险分级逐步扩展，目标是在安全边界内尽可能支持更多现有服务及外部操作；任何未注册 Tool、任意反射、任意 SQL、Shell、Python import 和本地文件副作用仍然禁止。
18. Workflow 只产出结构化执行结果、召回结果、状态补丁和可供 Java 使用的 Context，不直接产出最终用户回答。
19. 用户重试复用同一 `assistantMessageId` 和同一 `runId`，每次重试创建新的 `executionId/epoch`；旧 epoch 结果不得覆盖当前执行。
20. 终态回调使用独立 audience 的短期 JWT，Java 返回幂等 delivery ACK；回调目标只允许本机部署边界内的固定或受控地址，不接受用户输入的任意 URL。
21. 删除会话时 Java 立即写删除墓碑并使前端不可见，在同一事务写入持久化 Outbox；后台任务幂等取消 Workflow 并物理删除两端关联数据。清理完成前拒绝迟到回调和结果，长期记忆除外。
22. model-service 必须支持结构化输出/JSON Schema 契约、Workflow 服务身份校验、生产环境 Rerank fail-closed，并按 Plan/Rerank/Generate 所需能力提供就绪检查。
23. Context Hash 拆分为 `requestContextHash` 与 `snapshotHash`：前者覆盖创建 Run 时已经确定的原问题、短期 Context、权限范围和配置版本，用于 Run 幂等；后者覆盖执行后实际使用的 Query、记忆版本、知识片段和最终注入文本，用于复现和完整性校验。两者在对应阶段完成后均不可覆盖修改。
24. 只使用同一个物理 MySQL 实例，并按领域分为业务 Schema 与 `ylcloud_workflow` Schema。每类数据只有一个权威表，不在两个 Schema 长期重复保存：业务 Schema 保存消息、最终回答、最终 Snapshot、业务 Retrieval Trace 和长期记忆；Workflow Schema 保存 Run、Execution、Node、Event、Idempotency 和 Delivery。
25. Workflow 为交付和恢复保存的临时结果正文不属于第二份权威业务数据；Java 成功拉取并返回幂等 ACK 后删除正文或按短 TTL 清理，只保留必要运行元数据。
26. `POST /workflow-runs` 只有在 Run 与初始 Execution 已成功提交 MySQL 后才能返回 `202 Accepted`；进程内队列不构成可靠受理，服务重启后必须由数据库调度器恢复未完成 Run。
27. Docker 内回调使用固定 Compose 内部地址 `http://ylcloud-app:8080/internal/v1/workflow-callbacks`，不接受请求传入任意 URL，也不向宿主机公开该内部端点。
28. Java/前端状态为一级状态，Workflow Run 状态为二级状态。列表优先展示一级状态，详情页展示二级状态。映射为：`QUEUED ← QUEUED`（紫色）、`RUNNING ← PLANNING/VALIDATING/RUNNING`（蓝色）、`SUCCESS ← SUCCEEDED`（绿色）、`FAILED ← FAILED/TIMED_OUT/CANCELLED/ABANDONED`（红色）、`SUCCESS + degraded=true ← DEGRADED`（黄色）。
29. 第一阶段 Tool 目标范围包含只读、可控写入和高风险写入能力；高风险 Tool 必须取得本轮用户明确确认后才能调用，确认不得跨用户、会话、Run、Tool 或参数复用。
30. 继续使用现有 Assistant 页面、API 入口和 `knowledge_chat_session/message` 表，不新增通用 Assistant 页面。会话始终保持知识会话模型，但允许普通任务、知识问答和外部 Tool 在同一会话混合执行。
31. Workflow 通过 Java Knowledge Tool 编排知识库检索与长期记忆检索；Java 负责实际业务数据访问和最终回答生成。非知识任务默认不召回文档，只有用户明确要求或意图/依赖分析确认需要知识证据时才调用知识库检索。
32. 用户未明确选择知识库时，默认选择其个人知识库，即使知识库为空也可创建会话；Agent 可检查用户拥有或加入的全部授权知识库，并自动补充最多 1～2 个相关知识库，回答中必须披露实际使用范围。用户明确选择知识库后不得自动补充其他知识库。每次 Tool 调用前重新校验权限，已失权知识库不得参与召回。
33. 第一阶段外部 Tool 使用 SMTP、CalDAV 与 Web Search Mock；文件 Tool 仅访问 ylcloud 知识库。Mock 的契约、权限、幂等、确认和 E2E 测试通过即可视为第一阶段完成，真实 OAuth 接入后置。
34. 高风险确认支持 `ALLOW_ONCE` 与 `ALLOW_SIMILAR`：前者绑定准确 Tool 与参数摘要、单次使用；后者保存显式的 Tool/动作/资源范围规则，禁止无边界通配。规则可撤销，参数或资源超出范围时必须重新确认。
35. 第一阶段保留现有前端 2 秒轮询 `QUEUED/RUNNING` 的方式，刷新后从持久化消息恢复；不新增 SSE 或 Token 流式输出。
36. Workflow 成功但 Java 最终生成失败时，Java 一级状态为 `FAILED`，保留 Workflow `SUCCEEDED` 二级状态；重试复用未过期 Snapshot，只重跑 Java 生成。Snapshot 已过期时才创建新的 Workflow execution。
37. MySQL 8.3 以现有 Docker 镜像为版本基线。Snapshot 正文不额外加密；终端用户不得发起原始数据库查询，Java 与 Workflow 最小权限服务账号只访问各自 Schema，网站 Admin 通过受审计应用接口访问，数据库管理员及被授权系统账号按基础设施权限访问。用户接受数据库管理员、磁盘或备份持有者可能读取明文的风险。
38. 本轮环境基线为 Ubuntu 22.04、4 核 16GB、无 GPU、无独立测试或灰度环境。交付边界为本地 Compose 全量测试完成并形成发布候选，不执行生产部署；真实性能与外部服务联调保留为后续验证。
39. Java 应用只读取部署层注入的 Secret，不生成或管理宿主机 Secret；HS256 首版支持受控轮换，JWKS 后置。MySQL 备份由部署/运维层任务负责，Java 只负责业务保留、删除协调和可审计状态，不持有宿主机备份权限。
40. 跨仓库契约唯一来源位于 `ylcloud/schemas`，Python 与 Java 均按版本化 JSON Schema 校验；Java DTO 由 Schema 生成或通过生成一致性门禁验证，`new_project` 不维护独立权威副本。
41. 实施严格按 TASK 编号逐项推进：单项功能实现后立即生成并执行适用测试，完成一次正确性审查和一次安全审查；测试或审查失败则先完善该功能，不得进入下一项。通过后在受影响仓库分别创建包含同一 TASK 编号的规范提交，跨仓库提交记录互相关联，不混入无关修改。

## 固定意图

- 问答：`GENERAL_QA, EXPLAIN_CONCEPT, HOW_TO, COMPARE, SUMMARIZE, ANALYZE`
- 内容：`CONTENT_GENERATION, CONTENT_REWRITE, CONTENT_EXPAND, CONTENT_SHORTEN, TRANSLATION, FORMAT_CONVERSION, CODE_GENERATION, CODE_REVIEW, CODE_MODIFICATION`
- 记忆：`MEMORY_LOOKUP, MEMORY_SAVE, MEMORY_UPDATE, MEMORY_DELETE, MEMORY_CLEAR, MEMORY_CONFIRM, MEMORY_CORRECTION`
- 历史任务：`CONTINUE_TASK, RESUME_PROJECT, MODIFY_PREVIOUS_RESULT, RETRY, REFRESH_RETRY, ROLLBACK, TASK_STATUS_QUERY`
- 工具：`TOOL_EXECUTION, WEB_SEARCH, FILE_SEARCH, FILE_READ, EMAIL_DRAFT, EMAIL_SEND, CALENDAR_QUERY, CALENDAR_CREATE, REMINDER_CREATE, EXTERNAL_ACTION`
- 对话控制：`CONFIRMATION, CANCEL_ACTION, CORRECTION, HELP, UNKNOWN`
- 账户/数据：`ACCOUNT_OPERATION, PERMISSION_CHANGE, DATA_EXPORT, DATA_DELETE`

## 范围与非目标

- 包含：FastAPI Run API、Java Workflow Client、可扩展 Internal Tool Gateway、记忆全生命周期 Tool、受控外部操作 Tool、服务 JWT、MySQL Workflow Store、Graph 并行执行、Callback/对账、Docker Compose、可观测性、灰度和回滚。
- 不包含：前端任意 Workflow 上传，Shell/任意 import/本地文件 Tool，Workflow 直连业务 Schema/Qdrant，普通用户 Trace UI，跨小时审批工作流。

## 验收标准

- Docker 内 `ylcloud-app` 可以通过 `workflow-service:8003` 完成创建、查询、取消、重试和结果拉取。
- 同一幂等键不产生重复 Run、重复回答或重复 Tool 副作用。
- Workflow DB 账号对 YLcloud 业务 Schema 无权限，跨用户记忆泄漏为 0。
- 单 Run 无依赖节点最多 3 并行，Merge 结果不受完成顺序影响。
- Context 足够请求不调用长期记忆检索。未通过校验的记忆绝不进入 Prompt。
- Callback 丢失可对账恢复，旧 execution epoch 不能覆盖新结果。
- Workflow 不可用时普通问答可降级，高风险操作不可降级绕过。
- Snapshot 15 天、Trace 7 天、会话删除级联和过期重建提示通过自动化边界测试。
- Workflow 返回结构化 Context 后由 Java 生成并持久化最终回答；Workflow 结果中不得把模型生成的最终答复作为权威结果。
- 同一 assistantMessageId/runId 的重试只增加 execution epoch，迟到 epoch 无法写入回答。
- 会话删除成功后前端立即不可见；后台 Outbox 可持续幂等取消 Workflow 和清理两端数据，迟到结果无法复活会话。
- model-service 的结构化输出、入站鉴权、Rerank fail-closed 和分能力 readiness 通过契约及故障测试。
- `202 Accepted` 返回后即使 Workflow 进程立即退出，Run 仍能从 MySQL 自动恢复，不丢失已受理任务。
- 一级/二级状态映射、颜色和详情展示符合已确认规则；`DEGRADED` 不伪装为普通绿色成功。
- Retrieval Trace 不包含候选记忆正文，高风险 Tool 在没有本轮确认时一律拒绝。
- 普通任务不发生无关知识召回；自动知识库选择不超过 2 个、只使用授权范围并在回答中披露。
- 现有页面和消息表兼容；轮询、刷新恢复和混合任务通过前端回归。
- SMTP/CalDAV/Web Mock 与知识库文件 Tool 的契约、权限、幂等和 E2E 测试通过。

## 已选决策与风险接受

- 选用独立 Docker Workflow API，不在 Java 重写完整 Graph Engine。
- 同一 MySQL 实例，独立 `ylcloud_workflow` Schema/账号，对业务表无权限。
- 首版单 Uvicorn 进程，禁用 `isolated_process`；先完成 Linux Docker 验证再开放本地 Tool。
- 接受新增一个 Python 服务、内部网络往返和运维成本。
- 接受首阶段没有预设容量指标；在灰度阶段采集并建立并发、P95、最长运行时间、模型调用量和成本基线，再据此定标。
- 双 Hash、MySQL 分域单一权威、持久化后返回 `202`、Compose 内部回调、两级状态展示和高风险 Tool 确认门已确认。
- 接受 MySQL 8.3 与 Snapshot 明文存储风险；本轮以本地 Compose 验证完成为终点，不宣称生产上线或真实外部服务已验证。

## 2026-07-22 澄清记录与未决事项

### 已确认

- Workflow 是 Java 的编排工具，不负责生成最终回答；Java 继续负责最终回答。
- 记忆写入、更新、删除和清空均由 Workflow 调用 Java Gateway Tool。
- Tool 范围应在显式注册和安全门禁下尽可能扩展，包含受控外部操作能力。
- 重试复用同一 assistantMessageId/runId，并创建新 execution epoch。
- 回调采用独立 audience 的短期 JWT 和幂等 ACK。
- 会话删除采用后续确认的新语义：Java 同事务提交删除墓碑与清理 Outbox 后前端立即隐藏，Workflow 取消和两端物理删除由后台任务幂等完成；该决定取代早期“接口同步等待跨服务物理清理”的约定。
- model-service 增加结构化输出、服务鉴权、生产 fail-closed 和分能力 readiness。
- 容量与时延指标在首阶段灰度测量后定标，记录为已接受风险。
- `requestContextHash` 与 `snapshotHash` 分离并分别承担 Run 幂等和回答复现职责。
- 同一物理 MySQL 实例内按业务/Workflow Schema 分域，每类数据只有一个权威存储位置。
- Retrieval Trace 不保存候选正文。
- `202 Accepted` 仅在 Run 已提交 MySQL 后返回，并由数据库调度器恢复。
- 回调使用固定 Compose 内部地址。
- Java/前端展示一级状态，Workflow 状态作为详情页二级标签；`DEGRADED` 为黄色降级成功，`CANCELLED` 映射为红色 `FAILED`。
- 第一阶段覆盖只读、可控写入及高风险 Tool；高风险 Tool 强制本轮用户确认。
- Knowledge Tool 与 Memory Tool 均由 Workflow 编排，Java 负责数据访问与最终生成。
- Assistant 保持同一页面、API 和消息表，允许普通任务、知识问答与外部 Tool 混合执行。
- 默认个人知识库；无显式选择时可自动补充 1～2 个授权知识库并披露，显式选择后不再扩展。
- Mock Tool 通过即满足第一阶段，OAuth 接入后置。
- 高风险确认支持一次授权和有边界的类似命令授权。
- 保留现有 2 秒轮询，不新增 SSE/Token 流式输出。
- 删除改为前端立即不可见、Outbox 后台最终物理清理。
- 契约唯一来源为 `ylcloud/schemas`；生产基线按 Docker 的 MySQL 8.3。
- 本轮在本地 Compose 测试完成后结束，生产部署、真实外部账号联调和 OAuth 不在本轮完成范围。
- 代码实施采用“单一 TASK → 测试 → 正确性审查 → 安全审查 → 对应仓库规范提交”的门禁，不跨功能批量提交。
