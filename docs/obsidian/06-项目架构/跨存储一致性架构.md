# 跨存储一致性架构

## 问题本质

MySQL 事务不能回滚已经成功的 MinIO compose，也不能原子提交 Qdrant upsert。系统若在外部调用成功后直接返回 success，就会产生“对象有了但元数据没有”“向量有了但文档没有 chunk ref”或“数据库成功但向量缺片”等不一致。

YLcloud 不使用 XA，而采用业务状态机、幂等键、本地事务、提交后动作、精确校验、对账与补偿组合。

## 通用操作协议

~~~mermaid
sequenceDiagram
  participant API
  participant OP as cross_store_operation
  participant EXT as MinIO/Qdrant
  participant DB as 业务事务
  API->>OP: claim(operationKey, payloadHash)
  OP-->>API: RUNNING / 已有结果
  API->>EXT: 幂等外部操作
  EXT-->>API: externalRef
  API->>OP: 记录 externalRef/resultCandidate
  API->>DB: CAS/唯一约束下提交业务事实
  alt DB 成功
    DB-->>OP: afterCommit 标记 SUCCESS
  else DB 回滚
    API->>EXT: 补偿删除或保留为可重试候选
    API->>OP: FAILED
  end
~~~

operationKey 标识逻辑操作，payloadHash 防止同一键被不同请求复用。租约允许进程退出后其他执行者接管，resultCandidate 允许外部结果在数据库失败后安全重放。

## 分片上传一致性

上传分片使用 uploadId、chunkIndex、MD5 和租约。merge 必须：

1. 校验所有分片存在且大小正确；
2. 竞争合并租约，拒绝重复提交；
3. MinIO 合并后流式读取最终对象，一次计算 MD5、SHA1、规范 SHA256；
4. 在本地事务内创建 file_info 与 user_file，并将任务置为完成；
5. 提交后清理分片；
6. 摘要或元数据失败时删除最终对象全部版本，任务保持可恢复。

## RAG 一致性

RAG 使用更严格的“隔离后激活”：

- 开始构建时 document.vector_state=BUILDING，旧 active ref 不直接混入新结果。
- embedding 必须与 chunk 一一对应，维度和数值合法。
- Qdrant upsert 后按 documentId 精确计数。
- MySQL 在同一本地事务中启用 chunk ref，并把 document 提交为 SUCCESS/ACTIVE。
- 任一步失败进入 CLEANUP_PENDING，检索 SQL 排除该文档。
- 启动和定时任务比较 chunk_count、active ref 和 Qdrant point；不一致先隔离，再清理。

这保证对用户可见的是旧的完整版本或新的完整版本，不暴露半套索引。

## 删除和物理清理

逻辑删除、移除 Space 引用和物理对象删除是不同阶段。最后引用归零时先在 MySQL 创建 physical_file_cleanup_task，事务提交后触发执行器删除 MinIO 全版本、解析缓存和无效派生数据。进程退出后 recoverInterrupted/processPending 会继续处理。

## 一致性不变量

- SUCCESS 不能与零 chunk、零 active ref 或缺失 Qdrant point 同时成立。
- CLEANUP_PENDING/CLEANING 文档不能参与任何召回或引用。
- 同一活动上传、RAG 或画像任务受唯一约束/CAS 保护。
- 删除外部资源必须可重试；找不到资源应按幂等成功处理。
- 补偿任务本身必须持久化，不能只写日志。

## 取舍

该方案允许短暂的外部残留，但不允许错误数据对用户可见；以最终一致和可恢复换取避免 XA 的复杂性。代价是状态更多、需要对账任务和故障注入测试，但故障可以被解释和修复。
