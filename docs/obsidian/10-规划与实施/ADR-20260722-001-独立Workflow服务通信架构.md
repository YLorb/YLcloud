# 独立 Workflow 服务通信架构

## 架构决策

`new_project` 改造为 `workflow-service:8003`。`cloud-server` 是对前端的唯一业务入口，使用内部 JWT 调用 Workflow Run API。Workflow 是受控编排工具，通过 Java Internal Tool Gateway 统一编排知识库、长期记忆、会话和外部操作能力，可直接调用无状态 `model-service:8001` 的结构化 Plan/Embed/Rerank；Workflow 返回结构化结果和可注入 Context，最终回答由 Java 生成并持久化。

~~~mermaid
flowchart LR
  UI[cloud-frontend] -->|REST + 2s polling| APP[ylcloud-app]
  APP -->|Run API + Service JWT| WF[workflow-service:8003]
  WF -->|structured plan/embed/rerank| MODEL[model-service:8001]
  WF -->|scoped tool invoke| TOOL[Java Internal Tool Gateway]
  TOOL --> DB[(YLcloud business schema)]
  TOOL --> Q[(Qdrant)]
  WF --> WDB[(ylcloud_workflow schema)]
  WF -->|terminal callback| APP
  APP -->|reconciliation pull| WF
~~~

## 两阶段执行

1. Plan：验证身份/Context Hash，调用意图模型，生成唯一主任务、必要子任务和 Context 状态。
2. Validate/Compile：验证固定枚举、依赖、无环、最多 6 业务任务节点及安全一致性，编译为 Workflow v2 IR。
3. Execute：就绪节点最多 3 并行，节点只生成 State Patch，按稳定 nodeId 提交，Merge 后形成确定性的结构化结果和可注入 Context，不生成最终回答。
4. Deliver：回调只通知终态和 `resultHash`，Java 再拉取结构化结果、Snapshot Draft 和 Retrieval Trace，并由 Java 生成最终回答。

## Java → Workflow API

- `POST /internal/v1/workflow-runs` → Run 与初始 Execution 成功提交 MySQL 后返回 `202 + runId + executionId`
- `GET /internal/v1/workflow-runs/{runId}`
- `GET /internal/v1/workflow-runs/{runId}/result`
- `POST /internal/v1/workflow-runs/{runId}/cancel`
- `POST /internal/v1/workflow-runs/{runId}/retry`
- `POST /internal/v1/workflows/validate`（受限管理/测试）
- `GET /health`、`GET /ready`

创建请求必须包含：`workflowType/version`、`user/session/sourceMessage/assistantMessage`、原问题、短期 Context、`requestContextHash`、用户意图最大调用次数和运行预算。回调目标不得由请求传入，固定使用 Compose 内部地址 `http://ylcloud-app:8080/internal/v1/workflow-callbacks`。Header 必须包含 Service JWT、`Idempotency-Key`、`X-Request-Id`和 `traceparent`。

## Workflow → Java Tool API

`POST /internal/v1/workflow-tools:invoke`，使用 scoped Tool Token，绑定 `runId/executionId/nodeId/invocationId`。首批 Tool：

- `conversation.verify_context`
- `knowledge.list_accessible_spaces`
- `knowledge.search`
- `knowledge.load_chunks`
- `memory.search`
- `memory.load_versions`
- `memory.enqueue_conflict_cleanup`
- `memory.save`
- `memory.update`
- `memory.delete`
- `memory.clear`
- `web.search`（首阶段 Mock Provider）
- `email.draft`、`email.send`（首阶段 SMTP Mock Provider）
- `calendar.query`、`calendar.create`（首阶段 CalDAV Mock Provider）
- `file.search`、`file.read`（仅限 ylcloud 知识库文件）

后续 Tool 以显式 Registry 扩展到更多现有服务和外部操作。第一阶段目标覆盖只读、可控写入和高风险写入三类能力；可验证的 Mock Provider 计入首阶段完成。每个 Tool 必须分别定义输入/输出 Schema、风险等级、用户确认要求、幂等键、超时、重试与补偿语义。高风险写操作采用类似 Codex 的 `ALLOW_ONCE` 与 `ALLOW_SIMILAR`：前者仅对当前 invocation 生效，后者只对同一用户、同一 Tool、规范化参数边界和显式有效范围内的类似调用生效，并可审计、撤销；范围不匹配必须再次确认。不得因 Workflow 降级而绕过确认或权限检查。

Java Tool Registry 同时检查 Token scope、JSON Schema、用户隔离、风险和幂等。Workflow 账户不能直接访问业务 Schema/Qdrant。

## 会话与知识库选择

- 通用任务与知识库问答继续使用同一个 Assistant 页面、同一套知识会话 API，以及 `knowledge_chat_session/message` 表；同一会话允许普通任务、知识问答和外部 Tool 混合执行。
- 会话始终保留知识库会话属性，但是否召回文档由 Workflow 的意图与知识需求选择器决定。与知识库无关的任务（例如未要求参考文档的发邮件）不得仅因关键词相似而召回知识库。
- 用户未手动选择知识库时，以其默认个人知识库为初始范围；即使为空也允许选择。若完成任务确实需要其他资料，Agent 可检查用户拥有或加入的全部授权知识库，自动补充最多 1–2 个，并在回答中披露实际使用的知识库。
- 用户明确指定知识库后，该轮知识范围视为封闭范围，Agent 不得自动补充其他知识库。
- 每次知识 Tool 调用都重新校验当前用户权限；已撤销权限的知识库必须排除，不能依赖 Run 创建时的旧权限快照继续读取。

## 运行存储

MySQL 独立 Schema `ylcloud_workflow`：

- `workflow_run`
- `workflow_execution`
- `workflow_plan`
- `workflow_node_invocation`
- `workflow_event`
- `workflow_idempotency_record`
- `workflow_delivery`

只使用同一个物理 MySQL 实例，并按领域确定唯一权威位置：

- Java 业务 Schema：消息、最终回答、最终 Context Snapshot、业务 Retrieval Trace、长期记忆。
- `ylcloud_workflow` Schema：Run、Execution、Plan、Node Invocation、Event、Idempotency、Delivery。

同一业务数据不得在两个 Schema 中长期重复保存。Workflow 为结果拉取和恢复暂存的正文，在 Java 成功拉取并返回幂等 ACK 后删除或按短 TTL 清理；保留的运行元数据不得包含候选记忆正文。Workflow migration 独立管理，账号仅授予 `ylcloud_workflow` Schema 最小权限。

## 状态与幂等

- Run：`QUEUED, PLANNING, VALIDATING, RUNNING, SUCCEEDED, DEGRADED, FAILED, TIMED_OUT, CANCELLED, ABANDONED`
- Node：`PENDING, READY, RUNNING, SUCCEEDED, NO_USABLE_MEMORY, SKIPPED, FAILED, TIMED_OUT, CANCELLED`
- Run Key：`assistantMessageId + requestContextHash + workflowVersion`
- Node Key：`runId + executionId + nodeId + attempt`
- Tool Key：`invocationId + toolName`
- Result Key：`assistantMessageId + executionId + resultHash`

`requestContextHash` 冻结创建 Run 时的原问题、短期 Context、权限范围和配置版本；`snapshotHash` 冻结最终实际使用的 Query、记忆版本、知识片段和注入文本。前者用于 Run 幂等，后者用于复现和结果完整性，禁止相互覆盖。用户重试复用同一 assistantMessageId 和 runId，只创建新的 executionId/epoch。旧 epoch 迟到结果只记审计，不得覆盖当前回答。Callback 丢失由 Java 定时对账主动拉取。

### 两级状态

Java/前端一级状态用于列表主标签，Workflow Run 状态作为详情页二级标签：

| Java/前端一级状态 | Workflow 二级状态 | 展示 |
|---|---|---|
| `QUEUED` | `QUEUED` | 紫色底 |
| `RUNNING` | `PLANNING / VALIDATING / RUNNING` | 蓝色底 |
| `SUCCESS` | `SUCCEEDED` | 绿色底 |
| `FAILED` | `FAILED / TIMED_OUT / CANCELLED / ABANDONED` | 红色底 |
| `SUCCESS`，`degraded=true` | `DEGRADED` | 黄色底，明确标识降级成功 |

## 安全和隐私

- Service JWT 有效期不超过 5 分钟，绑定 audience、user/session/message/run 和 Tool scope。终态回调使用独立 audience 的短期 JWT，Java 必须返回幂等 delivery ACK。
- Workflow → model-service 必须经过服务身份校验；model-service 的结构化输出使用版本化 JSON Schema。
- 生产环境禁止 Rerank 离线 fallback 冒充有效结果；Rerank 不可用时 fail-closed。
- 前端不能直接访问 `8003`；生产 Compose 仅 `expose`。
- 禁止任意 Workflow、Shell、Python import、本地文件副作用和未注册 Tool。
- 敏感内容不进入回答、Workflow DB 和 Trace；管理诊断访问必须审计。
- Retrieval Trace 只保存 `memoryId/version/hash`、Query、分数、排序和淘汰原因，不重复保存候选正文。
- 首版服务认证使用独立 audience 的短期 HS256 JWT，并支持 active/previous secret 的受限轮换重叠期；JWKS 迁移列为后续任务。Secret 由部署环境注入，Java 只消费 Secret，不在应用进程内生成或管理宿主机 Secret。
- MySQL 以 Compose 的 `mysql:8.3` 为版本基线。业务层只有网站 Admin 可使用管理查询能力；系统层仅数据库管理员和被明确授权的系统账号可直接查询。Snapshot 正文不做字段级加密，接受数据库管理员、磁盘或备份持有者可读取正文及过期数据可能仍存在于历史备份的风险。
- 数据库备份、恢复、Secret 注入和轮换由部署/运维流程负责；Java 负责业务保留策略、清理任务协调和可审计状态，不承担宿主机备份系统职责。

## 删除语义

- 会话删除请求在 Java 同一事务写入删除墓碑、前端不可见状态和清理 Outbox 后即可幂等成功；前端立即标记为已删除，不再展示该会话。
- 后台任务基于 Outbox 重试取消 Workflow Run，并幂等物理删除 Java 与 Workflow 两端全部会话关联 Snapshot、Trace、Run 结果及运行数据；重复投递和部分成功不得造成恢复或遗漏。
- 墓碑是所有 callback/result/重试写入的强制门禁，迟到结果一律拒绝恢复业务数据。连续失败必须告警并保持可重试，不把“前端已删除”等同于“跨服务物理清理已完成”。
- 普通会话删除不删除独立长期记忆。

## Docker 与发布

- 基于官方 Python 3.11 slim 自建镜像，FastAPI/Uvicorn，非 root、只读根文件系统、`/tmp` tmpfs、healthcheck 和资源上限。
- 首版单 Uvicorn 进程；多实例前必须验证 MySQL lease、Poller 单活跃和并发拥有权。
- HTTP `202 Accepted` 只在 Run 与初始 Execution 已提交 MySQL 后返回；进程内 ThreadPool 只负责执行，不承担可靠队列职责。数据库调度器在启动和轮询时恢复未完成 Run。
- Compose 避免 `cloud-server <-> workflow-service` 循环 `depends_on`。Workflow Ready 只依赖自身和 Workflow DB，Tool 故障由单 Run 降级/重试。
- 目标环境基线为 Ubuntu 22.04、4 核/16GB、无 GPU、MySQL 8.3。本轮只做到本地 Compose 完整测试和发布候选，不执行生产部署；不存在独立测试/灰度环境这一事实必须写入测试结论。
- 本轮实现并在本地演练 feature flag、Plan/Retrieval shadow 和回滚路径；未来生产发布顺序仍为 Plan shadow → Retrieval shadow → 白名单灰度 → 全量。回滚关闭 feature flag，停止新 Run，Java 走当前 Context 降级链。
- 首阶段不预设容量和时延指标；本地 Compose 测量并记录并发 Run、各阶段 P50/P95、最长运行时间、模型调用量和成本，生产定标留待具备灰度环境后完成。
- 前端首阶段保持现有每 2 秒轮询消息状态，不新增 SSE/token 流式协议；`QUEUED/RUNNING` 生命周期与两级状态必须在轮询结果中完整呈现。

## 契约权威位置

跨仓库 JSON Schema 的唯一权威来源是 `ylcloud/schemas`。Java DTO 按版本化 Schema 生成或校验，`new_project` 只消费同步/生成产物，不维护第二份可独立演进的权威 Schema。

## 可观测性与验收

传递 `trace_id/request_id/run_id/execution_id/node_id/invocation_id/assistant_message_id`。按 Plan、Rewrite、Search、RRF、Rerank、Semantic Validation、Generate 分阶段记录 P50/P95、错误、重试和降级。RAG 验收必须包含 Recall@5/10、MRR、错误记忆率、矛盾率和跨用户泄漏，不只看最终回答。
