# 核心架构与执行流程

## 总体架构

项目采用 Planner-Executor 分层思想：

```text
用户输入
  ↓
Loader / Catalog / Selector
  ↓
WorkflowValidator
  ↓
SequentialWorkflowExecutor
  ↓
WorkflowContext
  ↓
LLMClient / ToolRegistry
  ↓
TraceRecorder
  ↓
WorkflowRunResult
```

其中 Level 1 主要关注 Executor，Level 2 增加 Planner / Selector。

## Level 1 执行链路

Level 1 从人工定义的 Workflow 文件开始：

```text
workflow.yaml / workflow.json
  ↓
WorkflowLoader
  ↓
WorkflowValidator
  ↓
SequentialWorkflowExecutor
  ↓
MockLLM / DeepSeekLLM / ToolRegistry
  ↓
WorkflowContext
  ↓
TraceRecorder
  ↓
final_output
```

典型流程：

```text
start
  ↓
llm: plan
  ↓
tool: search
  ↓
llm: summarize
  ↓
end
```

## Level 2 模板选择链路

Level 2 从用户 Goal 开始：

```text
用户 goal
  ↓
WorkflowTemplateCatalog
  ↓
RuleBasedTemplateSelector
  ↓
选择 workflow 模板
  ↓
填充 workflow.inputs.goal
  ↓
WorkflowValidator 二次校验
  ↓
SequentialWorkflowExecutor 执行
  ↓
Level2RunResult
```

当前模板包括：

- `research_summarizer.yaml`
- `python_error_analyzer.yaml`

当前选择器是规则选择器，不是通用 LLM Planner。它基于模板 metadata 中的关键词、优先级和 workflow 名称做稳定选择。

## 核心模块职责

### WorkflowLoader

负责把 JSON / YAML 文件加载成标准 Workflow 对象。

职责边界：

- 读取文件。
- 根据后缀分发到 JSON / YAML Loader。
- 解析为 dict。
- 交给 WorkflowValidator。
- 返回 Workflow 对象。

### WorkflowValidator

负责执行前结构校验和安全边界校验。

当前校验：

- start 节点唯一。
- 至少存在一个 end 节点。
- node id 唯一。
- next / if_true / if_false / loop body 引用存在。
- 所有节点从 start 可达。
- start 至少有路径到 end。
- tool 节点必须在 allowed_tools 白名单中。
- outputs 不重复，且来自 inputs 或 LLM / Tool 输出。

### WorkflowContext

Context 是运行时 key-value 共享状态。

节点不会把数据直接传给下一个节点，而是：

```text
节点输出 -> 写入 context[key]
后续节点 -> 按配置读取 context[key]
```

这样每个 key 的来源和使用都能被 Trace 与 Validator 检查。

### VariableResolver

负责解析 `{{ variable }}`。

关键规则：

- 如果整个字段是 `{{ search_results }}`，返回原始对象，保留 list / dict / int 等类型。
- 如果变量嵌入字符串，例如 `请总结：{{ search_results }}`，则把变量转成字符串。
- 支持 list / dict 递归解析。
- 缺失变量直接失败。

### ToolRegistry

负责把工具名称映射到 Python callable。

当前工具来源：

- 本地内置工具：`echo`、`mock_search`。
- Fake MCP Tool Provider：用于模拟外部工具来源。

ToolRegistry 不直接暴露任意 Python import，只能调用已注册工具。

### SequentialWorkflowExecutor

当前执行器是顺序执行器，不是完整 DAG 调度器。

已支持节点：

- start
- llm
- tool
- condition
- end

暂未支持执行：

- loop
- 并发 DAG

### TraceRecorder

负责记录每一步执行过程：

- node_id
- node_type
- status
- input
- output
- error
- context_before_keys
- context_after_keys
- context_diff
- duration_ms
- attempt

Trace 不记录完整 Context 快照，避免大对象重复占用内存。

## 与 LangGraph 的关系

当前项目不是 LangGraph 的替代品，而是对其核心思想的轻量学习版。

相似点：

- 都有节点。
- 都有状态传递。
- 都有工具调用。
- 都可以表达条件跳转。

不同点：

- 当前项目主要是顺序链和简单条件分支。
- 尚未实现复杂图调度、并发、循环执行语义和持久状态图。
- 当前目标是学习和可讲解，而不是生产级编排框架。

## Graph Workflow 目标架构

Graph Workflow 作为后续一级能力大类，采用“编译、分析、同步执行”三段式架构：

```text
Workflow
  ↓
Graph Compiler
  ↓
NetworkX Graph Analyzer
  ↓
SCC 分析与 Loop 缩点
  ↓
缩点后的 DAG 拓扑排序
  ↓
同步 Graph Executor
```

当前架构决策：

- 暂不引入异步或并发执行。
- 普通节点按照稳定拓扑顺序同步执行。
- Loop 是包含多个内部子任务的 Composite Node。
- Loop 对应合法且受控的强连通分量，由 Tarjan SCC 分析后缩点。
- 普通未声明环视为非法 Workflow。
- 当前继续使用共享 WorkflowContext。
- State Patch 是未来异步或并发执行前的必要改造。
- NetworkX 负责图分析，不负责节点执行、Context 修改、Retry 和 Trace。
