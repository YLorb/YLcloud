# Space 文件提交人与修改人可见性测试要求

## 交接门禁

实现 Agent/LLM 必须基于本文件生成完整测试用例和独立测试记录，记录环境、迁移版本、测试数据、步骤、预期、实际、日志/截图及结论。只有代码完成但未执行真实迁移、权限负例和 UI 验证时，TASK-20260816-001 只能标记 `pending-verification`。

## 必选测试范围

1. 单元测试：创建归因、不可变提交人、合格修改动作、非合格系统动作、空历史归因和用户占位映射。
2. 数据库迁移：从升级前数据执行 Flyway；保留 `created_by`，新增可空修改字段；重复迁移安全；禁止从 `updatetime` 错误回填。
3. 服务集成：直接上传、个人文件导入、Web 链接导入、文件夹创建、上传版本、恢复版本、重命名、移动和版本设置在事务成功后写入正确主体。
4. 系统状态隔离：RAG 排队、处理中、成功、失败、重试、移除清理和对账均不能改变最后修改人或用户修改时间。
5. 并发与失败：两个用户并发修改时最终归因与实际提交顺序一致；业务事务回滚时归因不能单独提交；幂等重放不伪造新的修改时间。
6. API/权限：成员按权限可见最小用户摘要；非成员、权限撤销者和跨 Space 文件 ID 均被拒绝；响应不包含邮箱、手机号或无关账号资料。
7. 用户生命周期：改名、离组、停用、注销、用户记录缺失和重名场景仍可稳定显示，且不会导致文件或版本列表整体失败。
8. 查询性能：列表、树和版本列表使用批量用户解析；用查询计数或等效证据证明文件数量增长不会产生逐行用户查询。
9. 前端/UI：桌面和窄屏均可访问提交人与修改人信息；未知/历史用户有明确文案；版本历史展示版本执行人；加载、空值和错误态正确。
10. 浏览器 E2E：至少两个成员依次执行上传、改名、上传版本、恢复版本和知识索引，逐步验证列表与版本历史显示。

## 专项通过标准

- 首次创建时提交人=最后修改人=实际用户；任何后续操作都不能改变提交人。
- 上传/恢复版本、重命名、移动、版本设置只在成功后把最后修改人更新为实际执行用户。
- 纯自动知识处理前后最后修改归因完全相同。
- 历史未知修改人显示未知，不使用 `updatetime` 或最近 Space 成员伪造。
- 无读取权限的主体得不到文件贡献者数据；有权限主体只得到稳定 ID 和安全显示名称。
- 所有后端测试、前端测试、生产构建和目标浏览器 E2E 通过，且有查询性能证据。
