# 首轮课程 RAG 问题定位与修复回归

## 1. 结论

首轮报告揭示了四个独立问题，不能笼统归因为“RAG 不准”：

1. 上传入口的产品上限、Spring multipart 上限和账号配额是三层不同限制；其中 Spring 20 MiB 配置错误已修复。
2. Q04 的 `0 context` 不能直接证明没有召回，因为旧响应会在生成器判定 no-answer 后清空检索证据；同时确实存在候选排序截断缺陷。两者均已修复并用真实 PDF 验证。
3. 约 110 秒延迟主要发生在查询改写和多路检索，不是最终答案生成。并行化后真实 Q04 从 131.4 秒降至 69.55 秒，但仍属 P1 性能问题。
4. TEAM Space 解散只有 outbox 生产者、没有消费者，导致永久停留在 `DISSOLVING/PENDING`。消费者和幂等清理流程已补齐，历史 Space 16 与新建回归 Space 均自动收敛。

本轮没有把 Q05–Q19 计入准确率；它们必须在不会重建后端容器的独占窗口重新执行。

## 3. 上传限制的正确边界

“支持 2 GiB”只表示 HTTP/对象存储入口允许该大小，不等于所有账号、所有知识化解析链路都能处理 2 GiB：

1. Spring multipart：当前默认单文件 2 GiB，请求额外保留 16 MiB envelope；超过时返回 413。
2. 账号/团队配额：仍可在 multipart 之后返回配额错误。本轮 Docker 测试账号上传 21.47 MiB 文件得到 429，证明请求已越过原 20 MiB Spring 限制；这不是 multipart 回归。
3. RAG 解析：当前 `ylcloud.rag.extraction.max-file-size` 仍为 50 MiB。不得为了匹配 2 GiB 宣传而直接把解析器内存上限提高到 2 GiB，否则会引入内存和拒绝服务风险。

后续产品语义应明确为：文件可存储至 2 GiB；知识化按格式和解析能力异步执行，超出知识化边界时文件仍可管理，但状态必须显示“未知识化/不支持”及原因。若要知识化超大文件，应实现流式/分段解析，而不是整体读入内存。

## 4. Q04 分层回归证据

测试库：`ylcloud_space_test`；文档：`第4章 地质年代与地质作用-.pdf`，12,229,777 bytes；默认知识化得到 126 chunks。

最终回答：标准化石延续时间短、演化快、分布广、数量多、特征显著，且易寻找和鉴定。该回答满足 Q04 的五个必需点。

| 指标 | 数值 |
|---|---:|
| retrieved chunks | 4 |
| final hit chunks | 4 |
| citations | 4 |
| rewrite | 28,814 ms |
| retrieval + rerank | 39,295 ms |
| generation | 1,443 ms |
| server total | 69,552 ms |
| client total | 69,673 ms |

这证明 Q04 已从“证据不可见且答案失败”修复为“召回、答案、引用均成功”。它不证明整个测试集 Recall@K 已达标，因为数据集目前只有期望文件名和答案要点，没有标注目标 chunk ID。

## 5. 性能问题仍需继续处理

本轮已经把延迟从约 110–131 秒降低至约 70 秒，但 70 秒仍不适合作为常规交互目标。阶段数据表明最终生成只占 1.4 秒，继续更换回答生成模型不会解决主要问题。

下一步方案按优先级执行：

1. 为改写、每条 embedding/Qdrant 路由、BM25/metadata 查询和 rerank 增加子阶段计时，避免把 39 秒归到一个黑盒。
2. 将多条查询 embedding 改为单次 batch `/embed`，然后执行 Qdrant 查询；不要在单 worker 模型服务上用多个 HTTP 请求制造竞争。
3. 根据 `precise/balanced/broad` 定义固定路由预算。默认 balanced 不应无条件同时执行 Multi-query、HyDE、Step-back 全部路线。
4. 对标准化后的 query plan 和 query embedding 加短期、按模型版本隔离的缓存。
5. 在独占环境至少运行 Q01–Q19 三轮，报告 P50/P95、各阶段耗时以及准确率变化，确认性能优化没有牺牲召回。

## 6. 解散消费者的一致性边界

清理顺序固定为：

1. 领取 outbox 租约；
2. 严格删除并确认 Space 的 Qdrant 向量；
3. 数据库事务内释放活动逻辑文件引用；
4. 物理引用计数归零时才提交物理删除任务；
5. 禁用 chunk 引用并清理 RAG 文档、Space 文件和成员；
6. Space 标记 `DISSOLVED`，事件标记 `SUCCEEDED`。

任何跨存储失败都会保留事件并退避重试，不使用危险 SQL 跳过状态机。重复处理 `DISSOLVED` Space 是幂等成功。
