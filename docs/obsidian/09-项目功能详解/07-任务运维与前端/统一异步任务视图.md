# 统一异步任务视图

## 产品目标

用户不应到多个页面猜测后台是否仍在处理。统一任务视图聚合当前用户有权查看的 RAG 索引和知识画像任务，展示来源、类型、状态、进度和错误。

## 聚合范围

AsyncTaskController 的 /api/async 调用 AsyncTaskService，聚合：

- space_rag_task：文件索引、空间重建、删除和修复；
- space_knowledge_pipeline_task：单文档和空间画像批次。

普通上传、分片上传和当前同步分片合并不进入该列表，因为它们有独立的前端进度与恢复协议。聚合必须按当前用户和 Space 成员关系过滤。

## 统一模型

不同任务表被转换为共同 VO：

- id 与 source；
- taskType；
- PENDING/RUNNING/SUCCESS/FAILED/SKIPPED；
- total/success/failed/progress；
- target 文件或 Space；
- errorMessage、created/started/finished time。

状态同名不代表业务完全相同，UI 还要显示 source 和 stage。例如画像 SKIPPED 需要展示 PROFILE_DISABLED 或 NO_ELIGIBLE_DOCUMENTS。

## 前端

`TasksPage.tsx` 通过 TanStack Query 轮询列表，使用语义状态组件区分运行、成功、等待和失败。任务来源保留为 `rag` 或 `knowledge`：RAG 失败任务只调用 RAG retry 接口，画像失败任务只调用画像 retry 接口，未知来源拒绝猜测并显示错误。终态通知从服务端持久计数恢复，不依赖浏览器内存；这对画像“成功 X、失败 Y”尤其重要。

前端测试 `TasksPage.test.ts` 固定验证三条规则：RAG 来源不丢失、画像来源不串线、未知来源不执行重试。

## 设计原因

采用查询聚合而不是立即创建通用任务总表，减少现有业务迁移成本；但若未来引入 MQ、统一重试和任务依赖图，可演进为公共 task registry。无论如何，业务原表仍应保留领域状态和不变量。

## 失败与权限

## 可点击任务详情

任务标题是可键盘访问的详情入口。`GET /api/async/{source}/{taskId}` 只接受 `rag` 或 `knowledge` 来源，并校验 `createdBy` 为当前用户；不存在和越权统一按不可见处理。详情模型包含状态、阶段、进度、成功/失败数、开始/结束时间、耗时、完成摘要、是否可重试和脱敏后的终止原因。

运行中详情每 3 秒刷新，进入终态立即停止；成功、部分成功和失败分别使用绿色、警告色和红色。详情内的重试复用来源对应的既有重试接口，不覆盖旧任务证据。服务端会截断错误摘要并清除 Bearer、API key、Token、密码、Secret 和带签名参数的 URL；异常栈只保留在服务端日志。

当前底层任务表只稳定保存聚合统计，尚无统一的逐文档 task-item/attempt 表。因此首版详情明确展示聚合结果；批量分项结果和重试链路属于数据模型演进，不能从容器日志临时拼接。

空任务返回空列表，不是 500。任务错误摘要脱敏并限长。用户退出 Space 后不能继续看到该 Space 的历史任务详情。
