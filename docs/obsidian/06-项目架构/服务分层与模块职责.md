# 服务分层与模块职责

## 业务后端分层

Spring Boot 后端是模块化单体。它保留一次进程内调用的简单性，同时通过包、Service 和持久化模型分离功能。

~~~mermaid
flowchart TD
  C[Controller 协议层] --> S[Service 业务与编排层]
  S --> M[Mapper 持久化层]
  S --> I[外部能力适配层]
  M --> DB[(MySQL)]
  I --> Store[MinIO/Qdrant/Model/Parser]
~~~

### Controller

负责 URL、请求 DTO、JWT 用户上下文和响应 VO。典型入口包括 FileController、SpaceFileController、SpaceRagController、KnowledgePipelineController。Controller 不应持有跨存储步骤或事务补偿规则。

### Service

负责业务不变量、权限、事务、任务状态和编排：

- FileService、MultifileService：个人文件与分片生命周期。
- SpaceService、SpaceFileService、SpacePermissionService：协作边界。
- SpaceRagService：RAG 索引与查询主编排。
- RagIndexTransactionService、RagIndexConsistencyService：RAG 提交和收敛。
- KnowledgePipelineService：画像流水线和资产治理。
- CrossStoreOperationService、CrossStoreRecoveryService：通用跨存储幂等与恢复。
- PhysicalFileCleanupService：最后引用归零后的物理清理。

### Mapper

MyBatis Mapper 对应单一聚合或任务表。复杂正确性不应只靠 Java if 判断，还应使用数据库唯一索引、CAS update 和事务锁。

### 外部适配

- MinioclientUtil 封装对象上传、合并、摘要读取、预签名和版本清理。
- QdrantVectorStoreService 封装向量写入、过滤检索、计数和删除。
- RagModelClient/HttpRagModelClient 封装 embedding、rerank、generate/chat。
- ParserServiceClient 与 DocumentParser 实现封装结构化解析。

## 前端分层

App.tsx 组织路由和全局选择；api.ts 统一后端调用；features 按用户任务拆分 auth、files、spaces、knowledge-base、knowledge、assistant、async、settings、share。multipartUpload.ts 与 fileHash.worker.ts 把大文件哈希和上传状态从页面展示中分离。

## 独立服务职责

| 服务 | 负责 | 不负责 |
|---|---|---|
| model-service | embedding、rerank、生成、readiness | 业务成功状态、Space 权限 |
| parser-service | 页面、布局、OCR、DOCX/结构解析 | RAG_READY 判定 |
| MySQL | 权威状态、关系、任务、审计 | 大文件正文、向量相似度 |
| MinIO | 对象、分片、版本 | 逻辑文件树和权限 |
| Qdrant | 向量点和过滤检索 | 文档权威状态 |

## 为什么暂不拆微服务

文件、Space、RAG 和画像共享大量事务事实与权限规则。过早拆分会把简单本地事务变成分布式协议，并增加事件顺序、重复消费和运维成本。当前用独立模型/解析服务隔离技术栈差异，把高耦合业务域留在单体，是更符合项目规模的选择。
