# Space 四角色与节点授权

## 目标、依赖与输入

- 目标：正式实现 OWNER/ADMIN/MEMBER/VIEWER，并由单一服务计算节点与子树 capability。
- 上游：ADR-20260817-001、现有 `SpacePermissionService`、`SpaceMemberService`、`AuthorizationService`。
- 下游：[[10-规划与实施/测试/TEST-20260817-101-Space四角色与节点授权测试要求]]。

## 修改范围与产物

1. `SpaceConstant` 增加 `ROLE_VIEWER`；`SpaceMemberService.normalizeRole`、DTO、前端类型与成员 UI 使用同一四角色集合。
2. 新建 `SpaceFileAccessService` 与明确的动作枚举，提供 `requireRead/requireCreate/requireRename/requireMove/requireDelete/requireVersionWrite` 和 capability 计算。
3. OWNER/ADMIN 可管理全部节点；VIEWER 只读；MEMBER 只能修改本人普通文件，目录操作要求目标和全部有效/隔离中后代均由本人创建。
4. 子树授权使用数据库查询，不递归加载 Java 对象；授权检查与写事务锁共享一致快照。
5. `SpaceFileVO` 增加 capability；列表、搜索、祖先链、版本、Workflow Tool 和开放 API 统一调用授权服务。
6. 部署所有者/显式管理员授权继续通过现有 `AuthorizationService`，不能被前端角色字符串覆盖。

## 不包含

- 文件 ACL 表、权限继承或成员自定义授权。
- 目录、导入和删除实现；由后续任务消费本服务。

## 验收、测试与回滚

- 四角色输入、存储、返回一致；前端不再提交后端拒绝的 VIEWER。
- 混合创建者子树对 MEMBER 返回 403；全本人子树允许；并发插入他人节点不能穿透检查。
- 后端仍是安全边界，隐藏按钮不作为授权。
- 回滚应用时保留 VIEWER 数据兼容读取；禁止把 VIEWER 静默提升为 MEMBER。

## 实施记录（2026-08-17）
