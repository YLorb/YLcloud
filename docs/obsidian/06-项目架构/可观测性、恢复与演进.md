# 可观测性、恢复与演进

## 可观测对象

YLcloud 的主要观测单位不是线程，而是持久化业务任务：

- upload_task/upload_chunk：分片接收、租约和合并状态。
- cross_store_operation：跨存储幂等键、租约、外部引用和结果。
- space_rag_task/document：索引进度、文档状态和向量状态。
- space_knowledge_pipeline_task/event：画像批次、阶段、成功/失败数和事件。
- physical_file_cleanup_task：物理对象清理重试。
- query/config/audit log：查询、配置和资产操作追踪。

## 恢复策略

| 故障 | 恢复方式 |
|---|---|
| Java 进程退出 | 数据库租约过期后接管；启动扫描未完成任务 |
| MinIO 临时错误 | 操作保持可重试，补偿或下次执行复用外部结果 |
| Qdrant 部分写入 | document 隔离，精确计数失败后进入清理状态 |
| MySQL 事务回滚 | 外部对象删除或保留 resultCandidate 供幂等重试 |
| 模型/解析失败 | 任务 FAILED，保留输入和错误摘要，可显式重试 |
| 清理过程中退出 | outbox/cleanup task 恢复 RUNNING 到可重试状态 |

## 观测原则

- 日志要包含 operationKey、uploadId、taskId、spaceId、documentId 等关联字段。
- 用户界面展示业务阶段和可操作原因，不直接暴露堆栈或凭据。
- 任务错误摘要要有限长度，原始详细日志由运行环境保存。
- “健康”要区分进程存活、模型 readiness、数据库迁移完成和业务端到端可用。
- 指标应覆盖任务吞吐、阶段耗时、失败率、补偿积压、检索质量与资源使用。

## 当前恢复机制

RagIndexConsistencyService 在启动和定时周期执行文档级对账；KnowledgePipelineTaskRecoveryService 回收画像超时任务；PhysicalFileCleanupService 恢复清理任务；MultipartUploadCleanupService 处理过期分片；CrossStoreRecoveryService 接管过期跨存储操作。

## 演进优先级

1. 先建立质量和运维指标，避免只看到技术成功率。
2. 将全部测试、迁移和 smoke 纳入同一 CI 发布门禁。
3. 当任务规模证明单体线程池不足时再引入 MQ，并保持现有幂等键和状态机。
4. 大规模向量重建采用 staging collection 与别名切换，减少在线索引空窗。
5. 知识画像先引入候选/审批/发布，再扩展独立索引或 GraphRAG。

架构演进必须由可观测瓶颈驱动。拆服务、上 MQ 或图数据库不能替代现有正确性不变量。
