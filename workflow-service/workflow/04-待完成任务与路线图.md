# 待完成任务与路线图

## 当前优先级判断

当前项目已经具备可演示、可测试、可写简历的基础。后续不建议直接跳到复杂 Level 3，而应该先补齐 Level 2A 的执行安全与输入统一能力。

推荐路线：

```text
Level 2A：统一输入格式 + 执行安全增强 + 示例库
  ↓
Level 2B 增强：LLM Selector / 更多模板
  ↓
Level 3：AI Goal -> Workflow
```

候选语义：

```text
LoopNode
  ↓
解析 items
  ↓
for item in items:
  context[item_var] = item
  执行 body 节点链
  ↓
全部完成后进入 next
```

## Context Store / Artifact Store

当前内存 Trace 主要记录 keys 和 diff；Graph Workflow 稳定版已确认由 SQLite 额外持久化 Trace、Context 审计快照和节点输出，详见 [[11-Run-Control与隔离Worker]]。

仍需后续补充独立的大对象 Artifact Store：

- MemoryContextStore。
- FileContextStore。
- run_id 隔离每次运行。
- 大对象按 key 保存到硬盘。
- Trace 只记录 context_refs。
- 大对象保存前脱敏。

Artifact Store 负责大对象和外部文件引用，不取代 SQLite RunControlStore 的控制记录与 JSON 审计数据。

## Graph Workflow 图工作流引擎

状态：Graph 骨架完成并通过自动化测试；Engine 稳定版架构确认中。

Graph Workflow 作为一个完整一级大类管理，不拆散到 Loop、Context 和 Executor 等多个平行路线中。详细架构决策见 [[08-Graph-Workflow图工作流引擎]]。

已确认：

- 新增显式 `edges` 的 Workflow v2；v1 通过 `V1ToV2Compiler` 保持兼容，新功能只使用 v2。
- 使用 NetworkX 完成拓扑排序、可达性、强连通分量和环分析。
- 当前只进行同步执行，由拓扑排序保证节点顺序。
- 节点记录 `pending / active / inactive / skipped / running / success / failed / timed_out / cancelled`；inactive 表示未激活，skipped 表示已激活但不执行并继续传播。
- 使用节点 ID 的词典序拓扑排序获得稳定顺序。
- Workflow v2 的条件放在 Edge 上；v1 Condition 节点由兼容编译器拆分为真/假条件边，并保留来源映射。
- Loop 由合法强连通分量缩点形成 Composite Loop Node，内部可以包含多个子任务。
- Condition 形成的环也必须归属于显式 Loop。
- 第一版使用单层 LoopFrame；未来支持嵌套 Loop 时再升级为执行帧栈。
- 当前继续使用共享 Context。
- 节点输出按节点和 Loop 迭代隔离，由 Merge 显式合并到公共 State。
- State Patch 延期到异步或并发执行之前完成。
- 下游需要的变量或字段必须在所有可能路径上补齐。
- Checkpoint 与恢复先作为待研究技术记录。
- 安全边界后续按照一次一个问题的方式确认。
- 本轮完成边界选择 Engine 稳定版，不包含 Level 3 Graph Generator、Checkpoint Runtime、异步和并发。
- GraphWorkflowExecutor 作为唯一核心执行器，Workflow v1 永久通过 v1 → v2 编译保持兼容。
- 外部简化类型内部统一为 JSON Schema，Pydantic 是 Schema 单一事实来源。
- Loop items 进入时求值一次；Loop 对外只发布最终结果，内部各分支先 Merge 为 collectItem。
- Loop Controller 的事件与状态机见 [[09-Loop-Controller运行时模型]]。
- Default Edge 仅在零条普通成功 Edge 命中时激活，且不承担异常路由。
- 新增 Error、Timeout、End Outcome Edge，详细设计见 [[10-Outcome-Edge与Timeout模型]]。
- Runtime 硬预算和 Context/Trace 超限策略已确认。
- Error/Timeout 恢复后到达 End 的运行状态为 completed_with_recovery；Retry 先于 Outcome Edge。
- Timeout 采用完整运行控制方案，见 [[11-Run-Control与隔离Worker]]。
