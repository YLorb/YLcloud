# 大文件分片上传

## 产品目标

大文件上传需要暂停、继续、失败重试和刷新恢复，网络抖动不能迫使用户从零开始。最终文件必须与客户端声明内容一致，并且并发点击合并不能产生重复记录。

## 客户端原理

multipartUpload.ts 组织初始化、状态查询、缺失分片上传和合并；fileHash.worker.ts 在 Web Worker 中计算摘要，避免主线程卡顿。客户端按固定 chunkSize 切片，为每片提供索引和 MD5，并保存 uploadId 作为断点标识。

## 服务端流程

1. MultifileController 调用 MultifileService.initfile。
2. initfile 校验摘要、大小、父目录、重名；命中内容可直接秒传，否则创建 upload_task。
3. uploadChunk 校验用户、分片索引、尺寸与 MD5，写入 MinIO 临时对象并持久化 upload_chunk。
4. status 返回已上传分片，客户端只补缺失项。
5. merge 通过 ChunkUploadLeaseService 取得唯一执行权，验证分片完整性后 compose。
6. validateMergedObjectDigests 流式一次读取对象，计算 MD5、SHA1、SHA256。
7. saveMergedFile 在 MySQL 事务中创建 file_info、user_file 和任务结果。
8. 事务提交后 cleanupPartsAfterCommit 清理临时分片。

## 为什么要三种摘要

分片 MD5 检测单片传输错误；整文件 MD5/SHA1 兼容现有协议和秒传；规范 SHA256 提供更强内容身份。最终对象必须从 MinIO 实际读取校验，不能只信任分片摘要拼接或客户端声明。

## 并发与故障

- uploadId 绑定用户、文件参数和父目录，恢复请求必须完全一致。
- 分片写入按 uploadId+chunkIndex 幂等。
- merge 使用数据库租约/CAS；并发请求只有一个提交，其余返回结果或 409。
- 摘要失败删除最终对象全部版本。
- compose 后数据库回滚清理元数据与外部对象，允许后续安全重试。
- 进程退出后分片和任务仍在数据库/MinIO，租约过期即可接管。

## 证据

故障注入 E2E 已覆盖缺片、错误摘要、八路并发、容器强制退出和元数据唯一键冲突回滚。核心测试还包括 MultifileServiceDigestTest 与 MinioclientUtil 摘要测试。
