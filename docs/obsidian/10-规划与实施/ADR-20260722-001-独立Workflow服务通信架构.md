# 独立 Workflow 服务通信架构

## 架构决策

`new_project` 改造为 `workflow-service:8003`。`cloud-server` 是对前端的唯一业务入口，使用内部 JWT 调用 Workflow Run API。Workflow 通过 Java Internal Tool Gateway 访问记忆和会话能力，可直接调用无状态 `model-service:8001` 的 Generate/Embed/Rerank。

~~~mermaid
flowchart LR
  UI[cloud-frontend] -->|REST/SSE| APP[ylcloud-app]
  APP -->|Run API + Service JWT| WF[workflow-service:8003]
  WF -->|generate/embed/rerank| MODEL[model-service:8001]
  WF -->|scoped tool invoke| TOOL[Java Internal Tool Gateway]
  TOOL --> DB[(YLcloud business schema)]
  TOOL --> Q[(Qdrant)]
  WF --> WDB[(ylcloud_workflow schema)]
  WF -->|terminal callback| APP
  APP -->|reconciliation pull| WF
~~~

## 两阶段执行

1. Plan：验证身份/Context Hash，调用意图模型，生成唯一主任务、必要子任务和 Context 状态。
2. Validate/Compile：验证固定枚举、依赖、无环、最多 6 业务任务节点及安全一致性，编译为 Workflow v2 IR。
3. Execute：就绪节点最多 3 并行，节点只生成 State Patch，按稳定 nodeId 提交，Merge 后生成回答。
4. Deliver：回调只通知终态和 `resultHash`，Java 再拉取完整结果、Snapshot Draft 和 Retrieval Trace。

## Java → Workflow API

- `POST /internal/v1/workflow-runs` → `202 + runId + executionId`
- `GET /internal/v1/workflow-runs/{runId}`
- `GET /internal/v1/workflow-runs/{runId}/result`
- `POST /internal/v1/workflow-runs/{runId}/cancel`
- `POST /internal/v1/workflow-runs/{runId}/retry`
- `POST /internal/v1/workflows/validate`（受限管理/测试）
- `GET /health`、`GET /ready`

创建请求必须包含：`workflowType/version`、`user/session/sourceMessage/assistantMessage`、原问题、短期 Context/Hash、用户意图最大调用次数、运行预算和 callback URL。Header 必须包含 Service JWT、`Idempotency-Key`、`X-Request-Id`和 `traceparent`。

## Workflow → Java Tool API

`POST /internal/v1/workflow-tools:invoke`，使用 scoped Tool Token，绑定 `runId/executionId/nodeId/invocationId`。首批 Tool：

- `conversation.verify_context`
- `memory.search`
- `memory.load_versions`
- `memory.enqueue_conflict_cleanup`

Java Tool Registry 同时检查 Token scope、JSON Schema、用户隔离、风险和幂等。Workflow 账户不能直接访问业务 Schema/Qdrant。

## 运行存储

MySQL 独立 Schema `ylcloud_workflow`：

- `workflow_run`
- `workflow_execution`
- `workflow_plan`
- `workflow_node_invocation`
- `workflow_event`
- `workflow_idempotency_record`
- `workflow_delivery`

Workflow migration 独立管理，账号仅授予该 Schema 最小权限。Java 业务库中的消息、Snapshot、Retrieval Trace 和长期记忆仍是权威数据。

## 状态与幂等

- Run：`QUEUED, PLANNING, VALIDATING, RUNNING, SUCCEEDED, DEGRADED, FAILED, TIMED_OUT, CANCELLED, ABANDONED`
- Node：`PENDING, READY, RUNNING, SUCCEEDED, NO_USABLE_MEMORY, SKIPPED, FAILED, TIMED_OUT, CANCELLED`
- Run Key：`assistantMessageId + contextHash + workflowVersion`
- Node Key：`runId + executionId + nodeId + attempt`
- Tool Key：`invocationId + toolName`
- Result Key：`assistantMessageId + executionId + resultHash`

旧 epoch 迟到结果只记审计，不得覆盖当前回答。Callback 丢失由 Java 定时对账主动拉取。

## 安全和隐私

- Service JWT 有效期不超过 5 分钟，绑定 audience、user/session/message/run 和 Tool scope。
- 前端不能直接访问 `8003`；生产 Compose 仅 `expose`。
- 禁止任意 Workflow、Shell、Python import、本地文件副作用和未注册 Tool。
- 敏感内容不进入回答、Workflow DB 和 Trace；管理诊断访问必须审计。

## Docker 与发布

- 基于官方 Python 3.11 slim 自建镜像，FastAPI/Uvicorn，非 root、只读根文件系统、`/tmp` tmpfs、healthcheck 和资源上限。
- 首版单 Uvicorn 进程；多实例前必须验证 MySQL lease、Poller 单活跃和并发拥有权。
- Compose 避免 `cloud-server <-> workflow-service` 循环 `depends_on`。Workflow Ready 只依赖自身和 Workflow DB，Tool 故障由单 Run 降级/重试。
- 发布顺序：Plan shadow → Retrieval shadow → 白名单灰度 → 全量。回滚关闭 feature flag，停止新 Run，Java 走当前 Context 降级链。

## 可观测性与验收

传递 `trace_id/request_id/run_id/execution_id/node_id/invocation_id/assistant_message_id`。按 Plan、Rewrite、Search、RRF、Rerank、Semantic Validation、Generate 分阶段记录 P50/P95、错误、重试和降级。RAG 验收必须包含 Recall@5/10、MRR、错误记忆率、矛盾率和跨用户泄漏，不只看最终回答。
