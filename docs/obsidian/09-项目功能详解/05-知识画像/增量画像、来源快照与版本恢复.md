# 增量画像、来源快照与版本恢复

## 产品目标

文件重新索引不一定代表语义内容发生变化。若只有 parser version、chunk ID 或检索来源变化，盲目重新调用 LLM 会浪费成本并覆盖人工编辑。增量策略需要判断“画像正文要不要重做”与“检索来源要不要同步”。

## 来源快照

KnowledgeSourceSnapshotService 从有效 RAG chunk 构造 KnowledgeSourceSnapshot，保存：

- 来源 chunk ID 集合；
- chunk 数量和字符数；
- parser version；
- 稳定 sourceSnapshotSignature；
- revision。

稳定签名基于有意义内容和顺序，而不是容易变化的数据库自增 ID。相同快照重复提交应幂等，不同快照并发更新通过 revision/CAS 检测冲突。

## 增量决策

KnowledgePipelineIncrementalService 返回 KnowledgePipelineIncrementalDecision：

- 完全未生成：执行完整画像。
- 内容签名不变、来源标识变化：SYNC_RETRIEVAL_SOURCE，只同步来源字段，不覆盖摘要、标签等画像正文。
- 内容实质变化或 schema/version 不兼容：重生成画像。
- 当前画像失败/无效：按恢复策略重试。

## 并发与事务

KnowledgeProfileWriteService 在事务内比较 expected revision 并更新快照、画像、问题、版本和审计。相同快照并发请求只有一个产生新 revision，另一个幂等返回；不同快照竞争必须报告冲突，不能最后写入者静默覆盖。

## 版本与恢复

每次编辑、重生成、分类或恢复形成 space_knowledge_profile_version。diff 比较两个快照；restore 不删除历史，而是从指定版本创建新的当前版本并记录 PROFILE_RESTORE 审计。

## 核心代码

- KnowledgeSourceSnapshot、KnowledgeSourceSnapshotService。
- KnowledgePipelineIncrementalDecision/Service。
- KnowledgeProfileWriteService、KnowledgeProfileAssetService。
- SpaceKnowledgeProfileVersionMapper、SpaceKnowledgeAuditLogMapper。
- V10、V17 等迁移。

## 设计原因

把来源同步与画像正文分开，保护人工运营成果并降低模型成本。revision/CAS 使并发行为可解释，异常事务回滚不会留下“快照已更新但画像未更新”的半状态。
