# 跨存储操作状态机

## 状态图

~~~mermaid
stateDiagram-v2
  [*] --> PENDING: 创建操作
  PENDING --> RUNNING: claim 获得租约
  RUNNING --> SUCCESS: 业务事务提交后确认
  RUNNING --> FAILED: 不可继续或补偿完成
  RUNNING --> RUNNING: 租约过期后接管
  FAILED --> RUNNING: 显式安全重试
  SUCCESS --> [*]
~~~

## 状态数据

cross_store_operation 保存 operationKey、operationType、payloadHash、resourceId、externalRef、resultCandidate、lease、attempt 和错误摘要。它既是幂等记录，也是恢复游标。

## operationKey 与 payloadHash

- operationKey 回答“这是哪一次逻辑业务操作”。
- payloadHash 回答“相同键对应的输入是否仍相同”。

若键相同但 payloadHash 不同，必须拒绝，避免调用者误把另一请求的成功结果复用到当前请求。

## 转移动作

CrossStoreOperationService.claim 使用 REQUIRES_NEW 事务独立争抢执行权；recordExternalRef 保存外部副作用；completeAfterCommit 只在业务事务真正提交后标 SUCCESS；afterCompletion 可发现回滚并保留恢复信息。

CrossStoreRecoveryService 扫描过期 RUNNING，按 operationType 判断是接管、验证外部结果、补偿还是失败。恢复程序不能绕过正常路径的不变量。

## 为什么状态记录使用独立事务

如果 operation 记录与业务事务一起回滚，数据库会忘记外部调用已经发生，恢复程序也找不到孤立对象。独立事务使“尝试过什么、外部产生了什么”即使业务提交失败仍可追踪。

## 终态语义

SUCCESS 表示业务事实和外部效果已经按协议收敛，不只是外部 API 返回 200。FAILED 表示本次尝试结束，但资源是否已清理仍需由具体 operationType 的不变量解释。
