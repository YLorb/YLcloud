# 问答可信度与知识一致性完整方案

来源需求：REQ-20261025-001。用户已授权实施。以下保留原设计基线；实际落地映射与验证状态见 [[10-规划与实施/测试/TEST-RUN-20261025-001-可信问答实施验证]]，不能将全部设计条目视为已完成。

实施采用现有 document.consistency_version 与 async task fencing 表示构建代次，新增不可变 chunk generation 和 knowledge_revision 清单；以唯一当前修订约束表示发布指针，未新增另一套 worker 系统。历史期限先约束读取，物理历史回收未启用。生成、Judge 与历史展示共同使用服务端证据及 answerId；Webhook 仅通知任务标识，答案通过当前授权接口读取。

## 1. 背景、目标与用户

面向知识库所有者、管理员、问答用户及运维人员，使回答可核验，文件更新/删除/撤权后系统行为可预测，并能定位失败与恢复。优先复用已有权限、配置日志、统一异步任务、Outbox、跨存储补偿与版本服务。

## 3. 已确认规则与草案默认行为

### 配置（知识库级）

| 字段（拟名） | 默认/校验 | 语义 |
|---|---|---|
| allowStaleDuringReindex | false | 仅在新版本构建期间允许继续使用最近一次已发布版本 |
| historicalEvidenceEnabled | false | 允许授权用户复核历史答案对应的旧版本 |
| historyRetentionDays | 默认不填；启用历史保留时必须为正整数 | 自该修订被替代的时间计算保留期限；UI 显示到期日 |
| configRevision | 服务端递增 | 并发配置编辑与请求策略快照标识 |

配置只允许所有者/管理员更新，服务端授权；成员只读有效行为，不能在请求参数或提示词中覆盖。允许范围上限由部署容量策略限制，不自行确定具体天数。

historicalEvidenceEnabled 控制知识库历史证据权益，不偷偷修改已有文件版本维护开关，也不扩大现有 VERSION_WRITE 权限。关闭时立即禁止知识库历史复核；已有物理历史按其原有保留权益处理，不能因关闭开关立即删除整个物理版本。

原文件没有历史版本维护时，知识入库仍需固定不可变内容版本以支持构建隔离；只保留当前有效索引所需对象。开启历史保留后，为后续被替代的修订增加保留权益。已被删除的数据不承诺恢复，历史缺口明确提示。

### 更新和保留细节（供审核）

- 更新时间以新版本元数据事务提交为准，上传失败/回滚不得使旧版本失效。
- 默认停用时立即停止旧版参与新回答；新版本失败也不自动恢复旧版。
- 开启旧内容过渡时仅允许已发布的旧修订，明确展示版本和过渡状态。若新版本失败，可展示失败状态并继续按该开关使用旧版，不假称最新；管理员可立即关闭。
- 过渡使用与历史复核是两种权益：即使历史复核关闭，允许过渡的旧版本仍可作为当前答案的证据；新版本发布后该过渡权益结束。
- 保留到期后逻辑历史访问立即失效，物理清理可异步滞后。延长期限只保护仍存在且尚未清理的内容，不能恢复已清理版本。
- 缩短期限先展示受影响版本数和将不可访问的日期，再由管理员提交配置；创建持久化清理计划。清理执行前重新检查最新配置，防止与延长期限竞态。
- 同一对象跨 Space 共享时，各库保留权益独立；物理对象只有在所有权益、当前引用和有效任务占用均释放后才可清理。

### 回答边界

模型分类为 POLICY / KNOWLEDGE / MIXED / UNKNOWN。用户明确禁止政策无依据推断，知识内容允许标记推断。草案采用：服务端政策标签/规则为强约束，模型只能收紧，不能将强约束降级；UNKNOWN 按严格模式处理。

MIXED 按子问题处理。政策关键条件不明时对应政策结论拒答，知识部分仍可独立回答。知识回答部分验证失败时，只保留独立成立且经验证的结论；若删掉失败结论会导致剩余内容误导，则整题拒答。这是拟定的失败策略，不把“部分通过”当成用户已确认的固定行为。

## 4. 方案比较

| 方案 | 满足度、风险与代价 |
|---|---|
| 仅提示词 + 非空引用 | 成本低，但不能阻止虚构证据、错误版本或语义不支持，不满足本需求 |
| 仅 JSON + 确定性校验 | 能防结构错误和伪造引用，但无法可靠判断证据是否证明结论 |
| 结构化结论 + 确定性校验 + 语义 Judge | 覆盖目标较完整；增加时延、费用与误拒答，仍需标注评测。为本草案主方案，待审核 |
| 全部人工审核 | 高价值政策可采用，但不适合所有交互式问答；作为可选后续路线 |
| 所有版本永久留存 | 实现简单、便于追溯，但成本不可控且违反有限保留需求 |
| 按 Space 保留权益 + 共享对象条件回收 | 能兼顾隔离与复用，但必须处理回收并发；为本草案主方案 |

不新增数据库、消息队列、模型供应商或分布式事务框架。Judge 可使用当前模型接入抽象，保留独立配置能力；同模型二次判断有相关性误判风险，不宣称“双模型即正确”。

## 5. 端到端问答流程

鉴权与策略快照 → 问题分类 → 确定版本/适用条件 → 多路检索 → SQL 权威状态复核 → Rerank → 构造证据包 → 结构化生成 → 确定性校验 → 逐结论 Judge → 输出前再次校验权限/资源代次/策略 → 服务端渲染与保存。

1. 检索约束覆盖 Space、文件、修订、索引构建代次、有效期和适用条件。向量结果只是候选，不是权限依据。
2. 证据包只包含实际送入模型的文本，保留表头、单位、脚注及必要相邻上下文。只有截断后仍存在的片段才可被引用。
3. 模型返回 status、questionType、claims、missingConditions；每条 claim 包含 claimId、text、FACT/INFERENCE、evidenceIds、适用条件和推断说明。返回类型与结构要进行 Schema 校验。
4. 模型不得决定预览 URL、对象路径、数据库版本或可访问权限。服务端把 evidenceId 解析为已授权证据。
5. 确定性检查：ID 白名单、证据未越界、原文区间/摘要哈希一致、结构与枚举、引用存在、政策禁止 INFERENCE、数字单位和条件字段的明显不一致。数字一致不等于结论正确。
6. Judge 检查支持/矛盾/证据不足，检查限制条件遗漏、主客体、时间、单位、否定和表格关系。知识推断需评价前提是否受支持、推导是否明显冲突，不要求原文逐字包含推断结论。
7. Judge 不得把“问题与文档相关”判定为“结论获支持”；判断输出必须引用 evidenceId 并提供失败原因。模型自报置信度不是校准概率。
8. 结构错误最多进行有界重试；改写、重新生成后必须重新完整校验。失败采用拒答或已验证的独立部分，不无限循环。
9. Judge 超时/服务故障返回暂不可验证，不转成“资料没有答案”，也不放行未验证回答。
10. 只渲染验证通过的 claims，不接受单独的自由文本 answer 绕过校验。不先流式发送草稿：一期只流式进度，验证完成后发送正文。

多知识库沿用现有分库结果输出，逐库保留策略、版本和结论类型；稳定 evidenceId 与 UI 编号分离。跨库综合若后续增加，综合结果必须重新验证，不能简单拼接后当作已验证新结论。

历史消息只能用于理解省略和对话意图，不是可直接信任的证据；引用和片段必须重新授权、重新检索或解析到有效证据。

## 6. 数据结构与状态设计

以下为逻辑实体，物理表名、索引及 Flyway 编号在实施时核对最新 dev 后确定。

| 实体 | 核心信息及约束 |
|---|---|
| 知识库配置扩展 | 两开关、保留天数、configRevision；配置变更沿用审计 |
| KnowledgeRevision（知识修订） | spaceId、spaceFileId、revisionId、fileVersionId、不可变对象定位、contentHash、createdAt、supersededAt；修订内容不原地改写 |
| IndexBuild（索引构建） | revisionId、buildId、resourceEpoch、taskId、attemptVersion、解析/切分/embedding 版本、清单哈希、状态；重试不混淆构建代次 |
| 当前发布指针 | currentRevisionId（文件当前）、publishedBuildId（已发布索引）；两者不同表示正在更新，是否允许旧内容由配置决定 |
| 历史保留权益 | spaceId、revisionId、retainedUntil、失效原因、状态；共享对象的权益不是共享访问权限 |
| Evidence（服务端证据） | evidenceId、spaceId、spaceFileId、revisionId、buildId、chunkId、contentHash、locator、实际提交文本的范围/摘要、来源标签和适用条件 |
| AnswerRecord/Claim | answerId、questionType、status、claims、evidence 关联、验证结果、配置/模型/提示词版本、生成时间；绑定用户和会话 |
| 删除/清理记录 | resourceEpoch、墓碑、清理对象版本与构建 ID、幂等键、重试时间、失败原因；不得在异步清理完成前丢失追踪信息 |

业务版本和时间语义分开：上传版本不等于政策版本，上传时间不等于生效日期。生效/失效日、适用地区、产品等元数据保存来源与可信状态；模型抽取值未经确认不能覆盖人工明确标签。缺少关键条件时不以文件最新上传时间代替。

修订可见性、索引构建状态、物理对象回收状态分开管理，避免一个 status 同时表达三种含义。

- 构建：PENDING → BUILDING → READY → PUBLISHED；异常 FAILED / STALE / CANCELLED。
- 清理：PENDING → RUNNING → DONE；失败 RETRY_WAIT / NEEDS_ATTENTION。
- 逻辑可访问性由当前权限、删除状态、发布指针、配置和保留权益共同判定，不仅依赖历史状态枚举。
- 无定位来源使用 UNLOCATED，不编造页码；旧数据无法绑定版本使用 LEGACY_UNVERIFIED，不批量伪造“已验证”。

## 7. 文件更新、删除和回收流程

### 更新

1. 校验修改权限、锁定逻辑资源；共享物理对象不能因一个 Space 更新而改变其他 Space 版本。
2. 当前基线存在物理文件级版本与元数据，需盘点传播语义。草案使用逻辑版本独立绑定；共享更新时采用写时分离或创建新不可变对象，不能全局覆盖共享内容。
3. 写新对象后，在同一 SQL 事务中登记新修订、推进 resourceEpoch/currentRevisionId、按策略更新检索资格、写重建 Outbox。事务失败由现有跨存储操作体系补偿外部对象。
4. 消费者按持久化任务构建，向量 ID/payload 包含修订和 buildId，重试有幂等键。
5. 校验对象内容、chunk 清单、向量 ID/数量/维度及构建归属，条件发布新指针；发布前重新检查资源未删除、版本与任务轮次匹配。
6. 旧构建转入保留/清理计划。旧 worker 只能清理自身构建，不允许按 fileUuid 粗粒度删掉新构建。

### 删除/移出知识库/撤权

1. 删除或移出时，SQL 事务先记录墓碑/不可见、推进 resourceEpoch、停用相关逻辑引用并登记清理任务。
2. 任务取消为辅助优化；真正防复活依靠所有发布入口的版本和状态条件。
3. 数据库不可见之后，即使向量还在，候选也无法通过权威状态检查。
4. 清理按 Space 逻辑引用与具体构建进行；共享物理资源仅在无有效权益时回收。
5. 撤权不删除共享内容，只改变访问结果与授权代次。所有证据读取、缓存命中、历史消息、预览下载都必须复核权限。
6. 输出前检查：模型调用期间发生删除/撤权/策略收紧，阻止原答案发送和作为可见消息保存；丢弃或有界重跑。

### 历史与缓存

- 历史引用只打开当时版本。过期/关闭/删除/撤权返回统一不可用状态，不泄露文件名或摘要，不自动指向最新版。
- 历史消息按 evidence 关联复核。草案在任一依据不可访问时隐藏整条助手正文，以避免混合答案残留敏感内容；细粒度隐藏可后续演进。
- 旧消息缺少可靠证据关联时标记未验证，不纳入新模型证据上下文。若无法证明当前可见性，不在受限知识库历史接口直接回传其正文。
- 缓存键包含主体授权上下文、Space、修订、配置和模型版本；命中后仍检查权限与有效性。缓存过期时间不能替代撤权检查。
- 受保护历史证据通过后端鉴权代理读取，避免长期可分享直链绕过撤权。已存在直链需要盘点有效期并退役，不能承诺旧直链瞬间撤销。

### 保留回收

到期扫描 → 生成回收候选 → 获取对象/权益并发保护 → 复查全部当前引用、各 Space 保留权益和活动任务 → 标记回收占用 → 删除准确对象版本/chunk/build 向量 → 条件更新结果。

新引用不能绑定处于回收占用的对象；延长保留与回收使用同一并发协议。垃圾回收崩溃可恢复；清理失败不恢复逻辑访问。不得仅靠一次引用计数查询后无锁删除。

## 8. 接口与前端改动

- 扩展现有 GET/PUT `/api/space/{spaceId}/rag/config`，加入两开关、保留天数和配置版本；并发修改返回冲突提示。
- 问答返回 answerId、status（ANSWERED/PARTIAL/REFUSED/UNAVAILABLE）、questionType、claims、citations 和原因码。保留兼容 answer 字段，但由服务端根据已验证结构生成。
- 拟新增受保护 evidence 解析/预览入口，输入稳定 evidenceId，服务端绑定用户与 Space；下载继续要求对应权限，不能仅凭 evidenceId 通行。
- 元数据编辑能力复用文件/知识设置，增加政策标签与适用条件管理，限定管理员权限并审计。
- 会话保存改为服务端 answerId 关联。兼容客户端旧消息上传时，不能授予 VERIFIED 状态或接受任意引用 URL。
- 知识设置页展示默认停用、过渡旧版、历史复核和期限；管理员显示保存控件，普通成员只读。
- 问答页分别展示事实、推断、部分回答、拒答和验证不可用；引用显示版本、适用日期、定位与过渡标志。
- 文档状态显示文件当前版本与索引版本差异、失败阶段、重试进度。RAG 可用性不与知识画像成功混为一谈。
- 预览支持 PDF 页码、PPT 页号、文本段落、表格工作表/范围；不支持精准定位时显示原因与可信原文摘要，不渲染未经净化的 HTML/URL。

拟新增的逻辑职责集中为三个模块，优先放在现有 cloud-server 和 cloud-pojo 内，不拆微服务：证据与可信回答、版本发布与保留、评测与诊断。配置与 UI 作为这些模块的适配层。

### 模块 A：证据与可信回答

说明版本 1；审核状态：待审核；产品规则依据：2026-10-25 用户确认分类回答；技术设计未确认。

1. **解决问题**：Q1—Q8 和 C5/C6。统一受权证据、逐结论校验及可信消息读取，不负责物理对象清理。
2. **不用会怎样**：现有文本回答与引用列表无法可靠绑定结论，历史正文也可能绕过引用鉴权；可以保留现有基础问答，但达不到本轮目标。
3. **核心结构**：Evidence、AnswerRecord、Claim、QuestionPolicy、ValidationResult，绑定用户/Space/修订和配置快照。
4. **调用链**：问答入口 → 分类/检索 → 证据包 → 生成 → 确定性校验/Judge → 最终授权检查 → 保存/展示；证据点击再次鉴权。
5. **设计理由**：把确定性安全边界与概率性的语义判断分开，防止模型生成路径直接成为权限凭证；代价为额外模型调用和拒答。
6. **替代方案**：仅结构校验更便宜但不能验证语义；人工审核适合少量关键政策；所有答案纯抽取降低生成风险但限制解释能力。
7. **面试讲法**：这是拟议方案：让每个结论绑定服务端证据，先验证证据身份和版本，再判断支持性；二次模型校验并不等于绝对正确。
8. **理解检查**：为什么非空引用不能证明结论？截断后的上下文怎样绑定 evidenceId？Judge 故障时为什么不直接返回原答案？

### 模块 B：版本发布与保留

说明版本 1；审核状态：待审核；确认依据：开关、默认值、管理员配置和可配置期限已确认；数据模型与回收协议待审核。

1. **解决问题**：C1—C4、C6—C9。管理逻辑知识修订、构建发布、保留权益和清理，复用现有文件版本/任务体系。
2. **不用会怎样**：仅在任务提交时加锁无法覆盖共享向量删除、更新调度失败与历史证据错位；单纯永久保留也不符合期限需求。
3. **核心结构**：KnowledgeRevision、IndexBuild、current/published 指针、resourceEpoch、保留权益、墓碑和持久化清理记录。
4. **调用链**：版本事务 → Outbox → 隔离构建 → 条件发布；删除事务 → 不可见 → 回收任务 → 复查权益 → 精确清理 → 对账。
5. **设计理由**：物理文件复用与逻辑版本权限分离；回收失败不影响逻辑安全，代价是更复杂的权益与构建记录。
6. **替代方案**：每 Space 完全复制数据更简单但成本更高；全局 staging collection 切换适用于批量迁移，本轮按文档构建发布粒度更小；保留旧单表原地更新难以并存新旧构建。
7. **面试讲法**：拟利用数据库事务决定“谁可见”，以版本栅栏拒绝过期发布，外部存储通过幂等和补偿达到可恢复一致性，而非声称分布式原子事务。
8. **理解检查**：旧任务提交被拒绝后为何还可能伤害新向量？两个 Space 保留期限不同时怎样回收？管理员延长期限与回收同时发生怎样处理？

### 模块 C：评测与诊断

说明版本 1；审核状态：待审核；依据：用户要求质量可量化；数值质量门槛尚待基线校准。

1. **解决问题**：Q8 及所有场景的验证。归因到解析、检索、生成、校验、授权或一致性阶段，不新增面向用户的自动审批能力。
2. **不用会怎样**：无法知道拒答增多是模型改善还是误拒答，也无法证明并发缺陷已修复；已有测试集可作为基础但需补标注和场景。
3. **核心结构**：版本化样本、预期证据与适用条件、人工标签、阶段 trace、失败码、评测报告；不收集无授权原始敏感内容。
4. **调用链**：固定数据/环境 → 执行场景 → 自动断言 → 人工盲审抽样 → 分层指标 → 发布报告；线上失败样本经授权脱敏后加入回归。
5. **设计理由**：自动门禁负责结构/权限，人工标注集校准 Judge；控制指标分母，防止靠多拒答提高表面准确率。
6. **替代方案**：仅 Judge 自动打分成本较低但形成自证循环；仅人工检查可解释但难持续覆盖，故草案采用二者分工。
7. **面试讲法**：拟把模型效果指标与安全不变量分开验收，并记录数据集和版本；没有真实运行证据不宣称质量提升。
8. **理解检查**：为何要同时统计误拒答和错误作答？引用准确率的分母是什么？如何避免生成模型给自己打分形成虚假提升？

这些理解检查不作为用户审批前置条件。三个模块均为待审核草案，未获实施授权。

## 10. 异常、恢复、性能与可观测性

- 失败码至少区分 NO_EVIDENCE、UNSUPPORTED_CLAIM、CONFLICTING_EVIDENCE、MISSING_CONDITION、STALE_REVISION、ACCESS_REVOKED、INVALID_OUTPUT、VERIFIER_UNAVAILABLE、INDEX_BUILD_FAILED、CLEANUP_RETRY。
- traceId 关联配置版本、修订、buildId、候选来源、过滤原因、精排前后排序、模型版本与各阶段耗时；普通日志默认不记录完整受保护正文或凭据。
- 模型调用不持有长数据库事务。使用短事务拍快照，外部调用后再次读取权威状态；不延长现有 query 上的事务到完整 Judge 调用期间。
- 超时、候选数、最大结论数、重试次数和模型并发均有预算；具体数值由当前部署基线确定，不写虚构性能承诺。
- 对账比较对象定位和哈希、有效 chunk ID 清单、构建 ID、向量 payload/维度、引用集合。数量相同不代表一致。
- 对不一致资源先隔离，再补偿或重建；反复失败进入可见的人工处理状态，不能无限隐藏重试。
- 文件的“可检索”以已发布构建完整性为准；解析完成、画像完成或任务投递成功都不是替代条件。

## 11. 安全和边界

文档正文视为不可信输入，不能让其中的指令修改分类、验证或权限规则。对 Judge 的输入也做数据/指令分离。外部模型只接收当前调用有权读取的最小证据；现有供应商与数据外发配置沿用，不新增第三方。

权限成功检查不能防止检查之后的无限时间变化。草案定义：以服务器输出前最后一次权威检查为访问判定点；检查前已提交撤权必须拒绝。大文件流在建立连接时鉴权，若要求中途撤权终止，还需活动流追踪；这不等价于收回已发送字节。正文一期验证后一次发布，避免泄露未验证草稿。

公开分享不自动成为知识问答权限；受保护引用不得借分享地址绕过证据鉴权。管理日志本身需权限和保留策略。

## 12. 迁移、发布与回滚

1. 新增兼容字段/表，不直接重写或删除现有历史对象；迁移编号核对实施分支后分配。
2. 盘点现有逻辑引用、物理版本和共享对象；能可靠映射才绑定 revision，不能映射则标记未验证并安排重建。
3. 为当前版本建立不可变修订和构建映射；旧向量逐步重建，不因迁移猜测版本或页码。
4. 默认写入两开关 false；历史期限为未配置。迁移不启动历史物理删除，清理先以只读候选报告验收。
5. 新旧 API 兼容期间 answer 字段来自受控结果；旧消息标记未验证，不能伪造验证通过。
6. 分库灰度，先验证默认严格读取、更新/删除/撤权，再开放历史保留和旧版过渡。
7. 旧 worker 需要停用/排空或增加构建协议版本门禁，禁止迁移后不懂新栅栏的 worker 写入新结构。
8. 回滚 UI 或 Judge 时保留权限、墓碑和版本栅栏；无法安全降级时停用相关问答，不恢复旧版不受控读取。已删除物理数据无法靠代码回滚恢复，必须依赖经验证的备份或明确不可恢复提示。

## 13. 验收指标与测试范围

安全/一致性门禁：预定义越权、跨库误删、旧任务复活、构建覆盖场景全部通过，测试中不得出现泄露或误删；这不是对所有未知攻击的绝对保证。

质量指标分开统计：

- 回答正确率：人工标注评测中的正确回答数/已作答样本数，同时报告作答覆盖率。
- 结论支持率：被证据支持的事实结论/全部事实结论；推断另计合理性与标注完整率。
- 引用准确率：确实支持对应结论的引用关联/全部引用关联；位置解析成功率另算。
- 无依据错误作答率：应拒答样本中给出无依据结论的样本比例。
- 误拒答率：可回答样本中不合理拒答的比例。
- 条件完整率、版本冲突识别率、改写拒答一致性、Judge 对人工标签的一致性/误判率、延迟 P50/P95 和单问成本。

本轮不擅自承诺 95%/99% 等数字；先建立中文固定基线，再确认可验收质量阈值。安全和确定性约束不因模型质量阈值未定而放宽。

测试覆盖：单元、回归、异常边界和安全测试；真实 MySQL/MinIO/Qdrant/MQ 集成；真实模型中文评测；浏览器权限与引用定位；并发版本更新/删除/回收/撤权；CPU/GPU 环境适用时分别验证模型预算。
