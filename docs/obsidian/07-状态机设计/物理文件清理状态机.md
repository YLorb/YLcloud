# 物理文件清理状态机

## 为什么清理是任务

用户删除的是逻辑引用，MinIO 中的物理对象可能仍被个人文件、Space 文件或版本引用。最后引用归零后才能删除全部对象版本。MinIO 删除不参与 MySQL 事务，因此需要持久化 outbox。

## 状态图

~~~mermaid
stateDiagram-v2
  [*] --> PENDING: 最后引用归零并入队
  PENDING --> RUNNING: 执行器抢占
  RUNNING --> SUCCESS: 对象全版本与派生缓存清理完成
  RUNNING --> FAILED: 外部错误
  FAILED --> PENDING: 重试
  RUNNING --> PENDING: 进程退出后恢复
  SUCCESS --> [*]
~~~

## 入队守卫

- fileUuid 有效；
- 当前业务事务删除或移除了最后有效引用；
- 相同物理文件的活动清理任务不会重复创建；
- 任务创建与引用变更在同一 MySQL 事务中。

## 执行动作

PhysicalFileCleanupService.enqueue 创建任务并在事务提交后发布事件；PhysicalFileCleanupExecutor 执行清理；MinioclientUtil 删除对象全部版本和删除标记；相关解析结果、chunk 等派生缓存按引用规则清理。

## 幂等与恢复

对象已经不存在应视为成功。recoverInterrupted 将异常中断的 RUNNING 恢复为可处理状态，processPending 周期扫描。重试必须再次确认没有新引用，避免清理任务排队后文件被重新复用。

## 与回收站的区别

移入回收站是逻辑可恢复状态，不触发物理删除；彻底删除且最后引用归零才进入本状态机。文件版本也属于引用，不能只检查当前 Space 节点。
