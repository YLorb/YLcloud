# 状态机基础与实现原则

## 从普通流程到状态机

普通同步函数可以写成 A、B、C 三步，因为调用栈仍在。只要流程跨越异步线程、外部服务或进程重启，就需要把“已经走到哪里”保存到数据库。状态机本质上是让流程进度成为业务数据。

## 实现方式

YLcloud 没有引入专门状态机框架，而是使用：

- 数据库 status/vector_state/stage 字段；
- Mapper 的条件更新实现 CAS；
- 唯一约束阻止同一资源出现多个活动任务；
- 事务保证一次转移涉及的多个表同时提交；
- lease_until/started_time 判断执行权与超时；
- 定时恢复服务扫描中间态。

这种实现直接、可查询，也更适合当前项目规模。

## CAS 示例

“把任务从 PENDING 改为 RUNNING”不应是先查再无条件更新，而应执行类似：

UPDATE task SET status='RUNNING' WHERE id=? AND status='PENDING'

只有 affected rows=1 的执行者获得任务。其他并发线程看到 0，必须停止。CAS 把竞争结果交给数据库原子决定。

## 转移设计原则

1. 只允许列出的转移，禁止任意覆盖终态。
2. 进入对外可见状态之前完成全部硬校验。
3. 外部副作用之前或之后都要有可恢复的持久化锚点。
4. 错误状态记录可操作原因，但不保存敏感信息。
5. 重试要么从安全中间态继续，要么先补偿回干净状态。
6. 定时恢复与正常执行必须使用同一守卫条件，避免双写。

## 状态与阶段

status 表示大生命周期，stage 表示 RUNNING 内部的细进度。例如知识画像任务可以是 status=RUNNING、stage=PROFILE_VALID。阶段适合展示和诊断，不应替代决定资源可见性的主状态。

## 常见错误

- 任务启动后立即标 SUCCESS，实际外部步骤仍在后台执行。
- catch 异常只写日志，不持久化 FAILED 或补偿状态。
- 重试无条件覆盖其他线程的新结果。
- 把“外部对象存在”当作业务提交成功。
- 一个 status 同时表达任务、资源、审核和启用开关，导致语义冲突。

## 如何阅读项目状态机代码

先找数据库字段和迁移约束，再找 Mapper 的条件更新，最后看 Service 的调用顺序与恢复扫描。只看 Controller 返回值无法判断状态机是否正确。
