## 面试讲解主线

建议按照这个顺序讲：

1. 我没有一开始做完全自主 Agent，而是先做确定性 Workflow Engine。
2. Level 1 负责执行人工定义的 Workflow。
3. Workflow 会先经过 Loader 和 Validator，保证结构、节点引用和工具白名单合法。
4. 执行器从 start 出发，按 next 或 condition 分支执行节点。
5. 节点之间不直接传参，而是通过 Context 的 key-value 状态传递。
6. ToolRegistry 控制工具调用面，避免 workflow 任意 import 或执行代码。
7. TraceRecorder 记录每一步输入、输出、状态、耗时和 context diff。
8. Level 2 把 Planner 和 Executor 分开，先从模板库选择 Workflow，再交给 Engine 执行。
9. DeepSeek 接入通过 LLMClient Protocol 完成，Executor 不关心底层模型厂商。
10. 后续 Level 3 会让 AI 生成 Workflow，但仍必须通过 Validator 和 Tool 安全检查。

## 可以重点展开的问题

### 为什么 Context 是 key-value

因为 Workflow 节点之间需要一个共享状态表。

LLM / Tool 节点只负责写入固定 output key，后续节点按配置读取需要的 key。这样数据流显式、可追踪，也方便 Trace 和 Validator 检查。

### 为什么不直接用 LangGraph

项目目标是学习 Agent Workflow 的底层机制，而不是直接调用成熟框架。先自己实现轻量版本，可以理解：

- 状态如何传递。
- 节点如何调度。
- 工具如何注册。
- Trace 如何记录。
- Retry 如何设计。
- Planner 和 Executor 如何分离。

后续可以接入或迁移到 LangGraph，但当前实现更适合作为学习和面试项目。

### 当前是不是 DAG

当前不是完整 DAG 调度器。

准确说法：

```text
当前支持顺序链和简单条件分支，Validator 会检查节点引用和可达性，但 Executor 仍是 Sequential Executor，尚未实现并发 DAG 调度和 Loop 执行语义。
```

### Mock Tool 测试有什么价值

Mock Tool 可以稳定验证完整链路：

```text
Loader -> Validator -> Executor -> Context -> ToolRegistry -> Trace -> final_output
```

它避免网络、真实搜索 API 和费用影响测试，让核心引擎可复现。

## 避免夸大的说法

- 完整复刻 LangGraph。
- 支持任意 DAG 并发调度。
- 支持通用自然语言自动生成复杂 Workflow。
- 实现生产级 MCP Server 编排。
- 开放领域模板选择准确率 100%。
- 真实 LLM 推理 P95 18 ms。

- 支持顺序链和简单条件分支。

- Mock Provider 下 P95 约 18 ms。
- 自建 40 条标注意图集上达到 100%。
