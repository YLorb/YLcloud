# Space 文件提交人与修改人可见性

## 目标与依赖

- 目标：让具有 Space 读取权限的成员在文件列表看到提交人、提交时间、最后修改人、最后修改时间，并在版本历史看到每个版本的提交人和提交时间。
- 上游：REQ-20260725-001、ADR-20260725-001、TASK-20260725-004；现有 `space_file`、`file_version`、Space 权限和用户显示名称能力。
- 下游测试：[[10-规划与实施/测试/TEST-20260816-001-Space文件提交人与修改人可见性测试要求]]。

## 修改范围与产物

1. 新增 Flyway expand 迁移，为 `space_file` 增加 `last_modified_by`、`user_modified_at` 及必要索引；保留 `created_by/createtime` 作为不可变提交归因。字段命名如需服从仓库既有规范，语义不得改变。
2. 新建文件、文件夹、直接上传、个人文件导入和 Web 链接导入时，在同一事务写入提交人及初始修改人。
3. 上传新版本、恢复历史版本、重命名、移动和修改文件版本设置成功时，在同一事务更新最后修改人和用户修改时间；提交人始终不变。
4. 审查所有 RAG/知识生命周期、对账、失败恢复和清理更新路径，保证它们不写最后修改归因。
5. Space 文件 VO/API 增加 `submittedBy`、`submittedAt`、`lastModifiedBy`、`lastModifiedAt`。主体采用最小安全摘要，至少含稳定用户 ID 与显示名称；批量列表必须批量解析用户，避免 N+1。
6. 版本历史 API 沿用版本 `created_by/createtime`，补齐安全用户摘要；上传新版本和恢复版本均显示实际执行用户。
7. 前端 Space 文件列表增加“提交人、修改人”信息及对应时间，版本历史增加版本提交人；窄屏下可以使用次级行或详情展示，但信息不能只能靠鼠标悬浮获取。
8. 用户已改名、离组、停用、注销或记录缺失时，使用“已停用用户 #ID”“已注销用户 #ID”或“未知”等安全占位，不返回邮箱、手机号等账号资料。

## 明确口径

| 动作 | 提交人 | 最后修改人 |
|---|---|---|
| 首次上传/导入/创建 | 写当前用户，之后不可变 | 写当前用户 |
| 上传新版本 | 不变 | 更新为当前用户 |
| 恢复历史版本 | 不变 | 更新为执行恢复的用户 |
| 重命名、移动、版本设置 | 不变 | 更新为当前用户 |
| 自动 RAG 索引、知识状态/错误更新、对账、清理 | 不变 | 不变 |
| 仅查看、预览、下载 | 不变 | 不变 |

## 历史数据策略

- 已有 `created_by/createtime` 直接作为提交人和提交时间；无法解析的用户保留稳定 ID 或显示“未知”。
- 现有数据没有可靠的最后修改人。不得使用会被 RAG 等系统任务更新的 `updatetime` 推断；没有确定业务证据时保持 `NULL`，直到下一次合格用户变更。
- 迁移和新旧应用滚动阶段，新增返回字段保持可空，旧客户端不受影响。

## 不包含

- 完整文件变更审计时间线、差异比较或审批流。
- 把 RAG/异步任务执行账号显示成文件修改人。
- Space 文件在线预览；由 TASK-20260816-002 独立交付。

## 验收标准

- 新建或导入文件后提交人与修改人均为实际用户，时间可追溯；后续合格操作只改变最后修改归因。
- 自动知识处理无论成功、失败、重试或对账，均不改变最后修改人和用户修改时间。
- 文件列表、目录节点和版本历史按口径展示贡献者；删除/停用/注销账号不会导致列表失败或泄露额外资料。
- 无 Space 读取权限的用户不能通过文件列表、详情或版本接口获得贡献者信息。
- 列表查询不存在按文件逐条查询用户的 N+1，分页/树形结果行为保持兼容。
- 历史无法归因的数据明确显示未知，不伪造修改人。

## 测试、风险与回滚

- 实现阶段必须覆盖 Mapper/Service 单元测试、Flyway 历史迁移、真实 MySQL 集成、权限负例、并发更新、API 契约、前端组件和浏览器 E2E，并创建独立测试记录回写本任务。
- 风险：技术更新时间与业务修改时间混用、漏掉写路径、用户查询放大、历史数据误归因。
- 回滚：前端/API 可停止展示新增可空字段；数据库列保留，禁止通过回滚迁移删除归因数据。
